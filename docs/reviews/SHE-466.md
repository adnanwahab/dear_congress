## Implemented behavior

`MapScreen.tsx` embeds a separate `NeighborhoodBudget` section using the existing
shell/navigation. `neighborhood-budget.ts` defines typed local allocations and a
100-credit limit. Three public project types can be dragged to any of nine
fictional blocks or selected and placed using native buttons. Replacements refund
the previous cost; removal and clear restore credits. Invalid drops and overspending
retain prior allocations and announce failure. A vertical list uses the same controls
and calculations; mobile CSS stacks blocks without requiring dragging.

Source `neighborhood-budget-v1` is an invented teaching fixture, with invented costs,
100 residents per equal block, clipped Manhattan-distance reach and unique-block
coverage. Benefits are declared potential uses, not measured usage or demographics.
The assumptions are visible in a disclosure. No source geography, journals, votes,
PR heads/bases, receipts, database, API or actual decision is read or written.
All allocations are component memory only and disappear on reload. The README and
public guide explain this separation. No new API or asynchronous fixture fetch exists.

## Acceptance checks and limits

- Automated model checks: exact budget, rejected overspend, replacement refund,
  invalid project/block, immutable prior state, edge clipping and overlapping coverage.
- DOM checks: project selection and native Place buttons (shared touch/keyboard
  path), rejection announcement, vertical list, removal, synthetic drop and clear.
- Existing county checks preserve provenance, revision counts and motion lifecycle.
  The county motion script now targets its own status rather than the first status
  on a page that has multiple independently labeled sections.
- Loading: bundled synchronous fixture; no added loading state or network dependency.
  Existing lazy route loading/error handling is unchanged.
- Failure: invalid drops/insufficient credits display a polite status and retain state.
- Reduced motion: this new section has no animations, timers or transitions; all
  information and interactions update immediately regardless of motion preference.
- Native drag, touch-device interaction, actual keyboard focus/reflow at 390px and
  200% zoom, forced colors and screen-reader announcements still require browser
  and human review under `docs/accessibility-acceptance.md`. DOM simulation is not
  evidence that those acceptance checks passed. No live reference was modified.
