## Units and reproducible formulas

Define a visit for this model as a session arrival, not a page view, account,
unique person or verified voter. Set an explicit session boundary in any future
consented measurement; this document introduces no tracking. One person can open
many sessions/devices; bots can create sessions. Existing page-view totals cannot
prove the session target. Do not infer people using IPs, fingerprints or cookies.

All scenarios have N=1,000,000 session arrivals and T=21,600 seconds:
`lambda=N/T=46.296296 sessions/s`. Average is not peak or concurrency.
The following are deliberately assumed sensitivities, not observed visitor mixes.
All bytes are decimal (MB=1,000,000 bytes; GB=1,000 MB).

Inputs per session: H=1 HTML read; A=asset requests reaching the network after
browser caching; R=API reads; W=civic mutation attempts; M=metrics POSTs;
D=mean active seconds; P=peak arrival multiplier; h=asset edge hit fraction;
B=total downstream MB across all network requests. HTML/API/metrics are conservatively
origin-bound. W includes retries; accepted unique mutations are modeled separately.

```
requests/session = H + A + R + W + M
average requests/s = lambda * requests/session
peak requests/s = average requests/s * P
origin peak requests/s = lambda * P * (H + R + W + M + A*(1-h))
average active sessions = lambda * D
approximate peak active sessions = lambda * P * D
six-hour downstream GB = N * B / 1000
average Mbps = lambda * B * 8
peak Mbps = average Mbps * P
```

Peak active sessions assumes peak arrivals last at least D seconds; use the
arrival-duration convolution for shorter bursts. Active sessions are not open
HTTP requests: at 300 ms mean service time, 1,000 requests/s implies about 300
in-flight requests by Little's law, excluding streams. p95 cannot substitute for
mean service time. Asset hit rates apply to static bytes/requests only; never
shared-cache personalized responses to attain this model.

For the mixed case, origin demand is `46.296296*5*(1+10+.3+3+10*.2)`.
Read/write mix at origin is therefore 13 read requests to 3.3 POST attempts per
session; only 0.3 are civic mutations. This distinction affects SQLite telemetry
and JSON storage differently. No edge cache deployment/hit rate is established.
B includes response bodies once; add measured headers/TLS, upload bandwidth,
third-party traffic and reconnect overhead separately. If assets are 1.0 MB of
the mixed 1.5 MB and their byte hit fraction is 80%, origin egress is 0.7 MB/session,
700 GB total and about 1,296.30 Mbps peak. Request hit fraction need not equal
byte hit fraction. A 10% retry fraction of original attempts adds 10% requests
on affected routes, while repeated retries can amplify load further.

A mass arrival cannot run at P times the mean for all six hours and still total
one million. For a 15-minute 5x burst, peak arrivals consume 208,333.33 expected
sessions; remaining 20,700 seconds must average 38.24477/s to preserve N.
Use a complete open-loop arrival schedule, including ramp and cooldown, rather
than multiplying the entire event by P. Account separately for polling after the
six-hour arrival window and sessions already active at its start.

## Storage and expensive work

Let u be accepted unique stored mutations per attempted civic mutation, b stored
bytes per accepted mutation, k index/metadata amplification, c retained full copies.
`logical growth GB = N*W*u*b/1e9`; `provisioned growth = logical*k*c`.
Use u=1 as a conservative illustrative storage case (not verified participation).

| Assumption/result | Browse/light | Planning mixed | Stress sensitivity |
|---|---:|---:|---:|
| b bytes/unique mutation | 2,000 | 4,000 | 8,000 |
| Logical six-hour growth GB | 0.10 | 1.20 | 8.00 |
| Growth with k=2 and c=3, GB | 0.60 | 7.20 | 48.00 |
| Unsampled request logs at 500 bytes/request, GB | 6.025 | 12.150 | 27.500 |

These are incremental budgets, excluding the existing dataset, temporary files,
SQLite WAL, checkpoints, audit receipts, metrics rows, queues and free-space
reserve. Logs are a sizing sensitivity, not a recommendation to retain identifying
requests; prefer aggregate metrics with reviewed retention. Page-view counts can
be aggregated but still incur per-request storage work. Set retention explicitly:
30 identical daily events at the mixed logical rate add 36 GB before compaction,
indexes or backups. Backup schedules and retention determine c; do not assume
three copies are a tested restore policy.

Current JSON persistence writes the entire snapshot, not b bytes. At an assumed
100 MB snapshot and mixed civic peak 69.44 saves/s, file write traffic alone is
about 6.94 GB/s, before serialization and atomic temporary-file headroom. This
is an illustration, not a measured DB size or disk throughput. Growing snapshots
and queued snapshot strings can exhaust CPU, memory and storage even if logical
growth looks small. Do not add writer replicas sharing/splitting this volume.
Verified repository voting uses separate governance SQLite and must be sized and
reconciled by repository + item kind + head/base revision, never pooled with
browser advisory choices. Likewise, keep source IDs and receipts distinct.

Model each heavy operation separately: if 1% of sessions request synthesis,
there are 10,000 jobs, 0.463 average jobs/s and 2.315 peak jobs/s at P=5.
At an assumed 2 CPU-seconds/job this alone requires 4.63 CPU cores at peak,
before HTTP/storage work; provider calls need quota, cost and concurrency budgets.
Streams require `active sessions * stream adoption` connections plus heartbeat
and reconnect traffic. None of these service times or adoption rates is measured.

## Reversible validation and rollout plan

1. Review this model and agree session definition, geography, scenario, route mix,
   retention, budget and proposed SLOs. Measure sanitized per-route byte sizes,
   service times and resource use in isolated staging with invented records at
   realistic cardinality. Record exact base/head, Bun version, topology and config.
   Remove credentials and outbound provider/GitHub actions; disable merge worker.
2. Build a target-allowlisted localhost/private-staging open-loop harness. No public
   host fallback. Use disposable stores; preserve fixture source/revision keys;
   reconcile accepted actions, changed/withdrawn choices and receipts after restart.
   Include metrics, cold/warm assets, retries, full-state reads and stream adoption.
   Start with 1 session/s, then 5, 10 and 46.3; advance only after review of each
   step. Cap generator concurrency and total requests and give the operator a stop
   control. First establish single-writer limits, rather than forcing unsafe scale.
3. Proposed gates, requiring human agreement: p95 origin reads <300 ms, writes
   <500 ms, unexpected failure rate <0.1%, zero lost/duplicated accepted records,
   stable memory and non-growing persistence queue. Report intentional 429s and
   their Retry-After compliance separately; rejecting demand does not meet capacity.
   Stop immediately on reconciliation failure, queue growth for 60 seconds,
   memory/disk >80%, unexpected errors >1% over a minute, or breached latency
   for two consecutive minutes. These thresholds are proposals, not active controls.
4. Repeat identical base/head runs with equal data, warmup and offered schedule;
   collect per-route p50/p95/p99, timeouts, offered/accepted/completed rates,
   CPU/RSS, queue age/depth, DB/WAL growth, bytes and generator lag. Account for
   coordinated omission. Only after gates pass, attempt 5x peak for an hour and a
   full six-hour arrival-window soak with bounded higher bursts; verify restart
   durability and perform an isolated restore. Stop/drain producer on failure and
   discard disposable data. A successful short smoke run is not a capacity result.
5. Any production change requires separate human review, all required checks and
   a human-published tagged release. Start with a small operator-approved exposure,
   watch the same metrics, and revert to the prior reviewed image on regression
   using a separately rehearsed data-compatible rollback. Never discard current
   votes, records or receipts to roll back. No rollout is authorized here.
