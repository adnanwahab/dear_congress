# SHE-924: versioned asset cache candidate

Refs: https://linear.app/shel-bernstein/issue/SHE-924/cs-l100063-cache-immutable-assets-aggressively-with-safe-versioned

## Evidence and scope

Audited this repository's README, browser builder, page renderer, real production
router, Dockerfile, release-parity docs, route smoke tests and launch merge policy.
GitHub search found no SHE-924 PR and found open related PR #332 (SHE-926), covering
public read API caches. This change does not modify API cache behavior.

Before: Bun already emitted hashed shell JS/CSS/favicon, with county geometry
bundled into JS. The asset handler had no explicit cache policy, method guard or
conditional response. Deferred map CSS, worker aliases and social image used fixed
paths. HTML used no-cache; /version used no-store. The runtime builds at startup;
images do not retain earlier releases' generated assets.

Candidate: exact build-manifest entries support GET/HEAD, validators and 304s.
IMMUTABLE_ASSETS=1 opts into public, max-age=31536000, immutable; unset/other values
use no-cache. Deferred MapLibre CSS and worker are built with hashed filenames and
injected into the client; public social metadata uses the hashed image. Fixed-name
compatibility aliases use no-cache. Missing asset-like paths return uncached 404s,
never an HTML shell masquerading as JS. HTML no-cache and /version no-store stay
unchanged. No personal responses enter this manifest.

## Local measurements

Bun 1.4.2, production build, in-process Request/Response API, no public requests:
26 non-HTML outputs, 5,995,140 bytes in full response bodies before conditional
handling; 26/26 matching validators returned 304 with zero response-body bytes
afterward. This is a deterministic body-transfer/reliability comparison across
all emitted assets, not network latency, wire bytes, browser-cache or fleet proof.
With an immutable fresh browser cache, reuse should avoid these requests entirely;
that prediction has not been measured in a browser here.

The manifest smoke builds production, development, then production again. It
checks HTML references, hashed map CSS/worker/media presence, no reused URL with
changed content in these builds, and stable rollback URLs. This is local artifact
validation, not a real deployment/rollback test. The route smoke adds policy
checks, validators, HEAD/POST, missing old-asset behavior and flag reversal, but
cannot bind a server in this execution environment.

## Reversible staged rollout — human release owner

1. Keep IMMUTABLE_ASSETS unset. Run all required checks in an environment that
   allows local sockets. Preserve the original approved image digest and manifest.
2. Before a mixed-fleet staging rollout, arrange an additive asset origin/archive
   shared by both revisions, or package both revisions' manifests in every serving
   image. Preserve exact bytes and MIME types; never redirect a missing old hash
   to a new hash or to HTML. No archive is implemented by this candidate. Until
   retention exists, do not enable this flag in production.
3. On isolated staging, use disposable state, two genuinely different approved
   production revisions A/B, and a client with an A shell but uncached deferred
   chunks. Serve B, fetch every A and B dependency (including map worker imports,
   CSS URLs and media), and assert bytes match the originating manifest. Verify
   HTML always revalidates, /version always refreshes, HEAD and 304 headers agree,
   and unknown assets fail closed. Repeat after restoring A, keeping B assets.
   Test different serving machines; a single response cannot prove convergence.
4. Enable the flag only on staging after retention checks pass. Use bounded,
   sequential read-only requests, one cold and one warm browser navigation to /
   and a configured map. Record UTC time, image digests, machine, manifest digests,
   statuses, request counts/body bytes and latency. Compare to the flag-off run.
   No public load test is authorized or needed.
5. A human reviews checks and authorizes a human-published tagged release through
   the existing gate. Start with a canary and repeat read-only parity and the
   cross-revision checks. Missing assets, stale shell/version or byte mismatches
   are no-go. Stop expansion and follow the existing compatible-image rollback
   process, retaining both manifests and production records.

Disabling the flag reverses future response policy but cannot revoke previously
cached immutable objects. Keep historical URLs byte-stable throughout the cache
lifetime and supported old-client window; an old page may request a previously
uncached lazy chunk long after deployment. Image rollback alone does not solve
that problem. Never delete/replace production records to test rollback.

## Validation and remaining acceptance

Focused build/cache/page tests pass. Typecheck passes. Required full suite and
route smoke were attempted; socket-bound integration checks fail with EADDRINUSE
on port 0 in this environment. Final run: 666 passed, 26 failed (692 tests); the socket startup failures
prevented the HTTP integration cases from executing. They must pass in CI before
human merge review. No deployment, rollback, public load test or browser latency
measurement was performed. Cross-release asset availability remains unimplemented,
so this candidate does not satisfy full rollout acceptance. Leave SHE-924 open.

Governance remains disabled/dry-run by default, quorum 10, 24-hour exposure,
current-head approval, fail-closed base/check allowlists and active kill switch.
No auth, vote isolation, source identity, ballots, receipts, production data,
release workflows or branch protections were changed. Main checks remain bun test,
bun run typecheck and route smoke test; at least one human approval is required.
The live protection/environment settings were not verified or altered. No external
messages, release publication, deployment, merge or auto-merge occurred.
