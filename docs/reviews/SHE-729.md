- `src/client/BillCatalog.tsx` renders exact imported fields and one HFL-051
  supplement. `src/shared/bill-catalog.ts` searches all fields independently of
  presentation. HFL IDs and per-entry revision digests already exist. The source

  equivalents, claim-to-source anchors, review attestations or legal-text versions.
  The separate supplement is illustrative and excluded from the catalog digest.
- `src/client/Dashboard.tsx` presents fictional workflow proposals and browser
  advisory choices. Its background link is not evidence for proposed legal text.
  Reusing these samples as official explanations would cross a source boundary.
- `src/client/TopicHubs.tsx` preserves stored topic/need/proposal lineage and uses
  `ProposalProvenance`. It deliberately has no reviewed official-bill/topic mapping.
  Do not infer this binding from titles or shared topic labels.
- `src/client/ProposalProvenance.tsx` already rejects unsafe reference URLs and
  labels missing, future or over-30-day check dates unavailable/not checked.
  `src/shared/legislation.ts` separately models 24-hour metadata freshness and
  failed refreshes. Neither freshness clock proves legal-text review.
- The official lane is metadata only. Full text, amendments, reviewed legal status
  and effective-date citations remain prerequisites documented in
  `docs/legislative-metadata.md`. An accessible background URL alone cannot prove
  factual equivalence across reading levels.

The requested reviewed content is absent from the audited inputs. Agent-authored
condensation cannot supply a human review attestation. A UI could be built around
explicitly hypothetical fixtures, but that would still leave the central reviewed
bill-explanation requirement unmet. This change records the implementation contract
rather than publishing invented review or authoritative legal content.

## Concrete implementation contract

1. Add a separately versioned editorial artifact keyed by source kind, original
   item ID, immutable source revision and language. Keep HFL, workflow, citizen,
   official and repository PR identities separate. Include ordered claim IDs,
   three reviewed renderings, exact source document/section anchors, checked date,
   review revision and reviewer provenance. Digest all layers and supplements;
   catalog hashes alone are insufficient. Review must explicitly cover retained
   qualifications, exceptions, dates, uncertainty and proposed-versus-enacted status.
2. Validate before rendering: missing anchors/review, changed source hashes or
   unsafe URLs must expose an unavailable/unreviewed state. Hypothetical claims
   must carry that label at every depth. Keep source access and freshness warnings
   visible at the gist level. Stale evidence must not acquire a fresh review date
   when the reader changes depth or refreshes metadata.
3. Use a native labeled three-choice control (30-second gist, practical detail,
   full source context) as the complete static experience. Any elastic animation
   should enhance the same control. Keep DOM claim order and IDs stable; preserve
   focus on the control, selected bill, search, category and topic context. Avoid
   drag-only navigation, runtime summarization, mandatory canvas or motion.
4. Store depth in the URL while preserving existing parameters and source identity.
   Handle popstate, invalid depth and direct deep links deterministically. Preserve
   current full-field search regardless of depth. Keep source targets addressable
   at every depth; do not leave fragment links pointing into hidden content.
5. Integrate first in the catalog detail view, then use the same renderer in
   Dashboard and TopicHubs only for explicitly reviewed bindings. Reuse existing
   source presentation without representing background references as legal claims.
   No data migration, new voting endpoint or changes to participation are needed.

## Acceptance and test plan

All three acceptance criteria remain open. Existing catalog tests cover search,
empty search results, filter intersection, reset, simulated popstate and zero
writes. That is not coverage of an empty reviewed-layer dataset or a new dial.
Existing native browser catalog tests are a useful starting point, not acceptance
evidence for this feature.

Add fixtures for empty layers, rejected/missing anchors, changed revisions,
unreviewed content, stale/future timestamps, failed refresh and hypothetical claims.
Verify each significant claim retains its accessible source or hypothetical label
at every depth, including qualifications. Test stable claim order and focus,
unchanged selection/search results, URL reload, actual browser back/forward,
keyboard operation and no writes. Repeat the complete journey in static/low-power
and reduced-motion modes, narrow mobile and zoom. Verify no animation is required
to reveal sources or change depth. Human legal/editorial review, screen-reader
navigation and live source accessibility checks remain necessary.
