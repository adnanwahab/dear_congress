## Rate and uncertainty rules

For a future session conversion rate, numerator must be sessions with at least
one accepted advisory action; denominator must be measured eligible sessions
from the same cohort and window. Raw saved-vote counts divided by page views are
not session conversion and can exceed 100%. Existing credential-free views and
separately observed writes cannot establish this join. Any optional session/action
association must avoid retaining political choices, journal text or voter IDs in
analytics and must not alter ballot authorization or persistence.

For a binary rate with n > 0 and x successes, a proposed 95% Wilson interval uses
z = 1.96, p = x/n, d = 1 + z²/n, center = (p + z²/(2n))/d and half-width =
z × sqrt(p(1-p)/n + z²/(4n²))/d. Display center ± half-width bounded to [0,1].
For n = 0 show unavailable. This is conditional model uncertainty, not a bound
on bots, missed events, nonresponse or civic representativeness. Repeated requests
and sessions are correlated; label the independence assumption and avoid treating
a narrow interval as evidence of a representative population.

Each metric needs the same visible bot caveat: automation can inflate events and
actions; JavaScript blocking, failed delivery, rate limits and crashes can reduce
observations. No current bot detector provides a defensible human-only count.
Never invent a bot-adjusted estimate or display a unique-person total.

## Channel quality and privacy

Current collection omits referrers and channel attribution. Do not rank channels
by action quality from today's aggregate counters. A future implementation can
use a small allowlisted campaign code, with unknown/direct explicitly grouped,
without storing full referrer URLs, query strings, contact details or arbitrary
campaign text. Never accept client claims as proof of a completed action.

Proposed session/revisit definitions change the README's existing promise of no
page-view visitor IDs or new cookies. This review does not implement that change.
Before adding identifiers, specify consent, purpose, expiry, deletion and retention
in the public guide and privacy flow, including storage-blocked behavior. Do not
link analytics to verified merge identities. If tracking is declined, retain
credential-free aggregate views and show missing session coverage explicitly.

Usefulness and comprehension need a separate voluntary, stance-neutral question
(for example, whether the reader understands that participation is non-binding).
Show response count, question wording and nonresponse limits; do not infer either
from sharing, dwell time or a large page-view number. No contact scraping,
automated outreach, stance rewards or governmental-authority claims are proposed.
Keep the independently operated, non-binding beta description visible.

## Implementation and human acceptance checklist

- Add separate dashboard rows for all five measures with explicit unavailable
  states, definitions, source, collection window and health. Preserve existing
  stats tables and origin/scope distinctions; never backfill inferred sessions.
- Review and implement the session/revisit privacy contract before collection;
  test inactivity boundaries, expiration, blocked storage, multiple tabs and
  restarts. Never use analytics tokens as voter authentication.
- Add a bounded error-rate snapshot using the existing API observation boundary;
  keep process-local five-minute coverage distinct from durable daily counts.
- Test source/repository/kind/head/base isolation, rejected and repeated actions,
  recording failures, sample separation, zero denominators and interval edges.
- Run `bun test`, `bun run typecheck`, `bun run test:routes`; verify protected
  dashboard HTML and desktop/mobile layout with isolated local data. Screenshots
  of `/` or `/votes` alone do not prove `/admin/stats` acceptance.
- A human verifies the current revision and deployed-source alignment before any
  acceptance decision. A passing agent or merged review document is insufficient.
