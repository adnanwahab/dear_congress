# SHE-978 — release correlation review

Refs: https://linear.app/shel-bernstein/issue/SHE-978/cs-l100089-correlate-release-version-with-failures-in-privacy-safe

Status: partial implementation, awaiting human review and integration. Do not close
this issue or treat this document as acceptance.

## Evidence and change

Read repository instructions, README, launch alerts, release parity and merge policy.
GitHub searches for repository PRs matching `telemetry` and `SHE-978` returned none.
The version search returned PRs 120, 123 and 124; their descriptions concern native
simulation and screenshots, rather than error reporting. PR 123 notes unresolved
production source identity. The supplied live `/version` could not be accessed by
the web tool; this review does not assert its current contents.

The checkout has no BugSnag SDK or external deployment dashboard integration.
Its identity comes from the image manifest, with no runtime SHA override. Local
unidentified builds remain explicitly null/unknown rather than inventing a SHA.

Implemented server response observation emits only buildSha, registered
routeTemplate and numeric status for HTTP failures. Unknown paths share
`unmatched`; exception names, messages, stacks, request URLs, bodies, cookies,
referrers and identities are excluded. Both returned failures and thrown handler
errors pass through the observer, after API security validation. Internal metrics
errors retain a separate fixed category rather than implying a failed user write. The first-party `/api/error-report` accepts only buildSha, routeTemplate and one
of two fixed categories, with a 512-byte bound, same-origin validation and an
independent IP rate limit. It issues no identity or cookie. Browser reports omit
credentials and referrers and are capped at ten per document. No third-party SDK
or third-party telemetry transmission was added.

`/version` now includes the exact served browser asset paths. The browser entry
embeds the image manifest SHA in `document.documentElement.dataset.assetBuildSha`.
Authenticated GET `/admin/deployments` exposes per-template/status counts for the
current build and a version split of unverified browser reports, explicitly
scoped to this process since startup. At most 20 browser versions are retained;
unknown is a distinct version. Submitted SHAs are labels, not trusted attestation. It uses existing
stats authentication, no-store and noindex. Counts reset on restart; they are not
fleet totals or unique affected users. The summary adds no persistent storage.

The protected deployment page shows server failures and a browser version-split
table. It is a local diagnostic view, not a configured external fleet dashboard.

## Remaining acceptance

- Browser runtime errors and unhandled rejections use fixed categories; handled
  application failures are covered by server HTTP failures when applicable. No
  stack/message grouping or automatic breadcrumbs are collected. Module fetch
  failures before the entry executes cannot report through that entry.
- The existing external deployment dashboard is unavailable in this checkout.
  Its operator must aggregate PUBLIC_ERROR records by buildSha, routeTemplate,
  status and time; expose counts and a version split across serving machines.
  Keep unknown revisions visible. Per-process diagnostics cannot prove fleet split.
- After a human-published tagged release, compare `/version` commit with the browser
  assetBuildSha and manifest assets across machines, including rollback and stale
  clients. Verify safe synthetic failures outside production and inspect outbound
  payloads. Do not send test telemetry or mutate production without authorization.
