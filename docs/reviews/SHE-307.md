## Proposed additive contract

These records and operations are design requirements, not existing endpoints.

1. A deliberation references a stable source proposal ID and source identity;
   preserve journal citations and repository/item-kind boundaries. Do not reuse
   PR ballot tables or infer consent from journal text, comments or map models.
2. A published revision contains an immutable ID, parent ID, complete text/hash,
   source citations, author attribution, timestamp and reviewed redline. Private
   working drafts can change; publishing creates a new snapshot. Existing votes
   and receipts continue to reference exactly the text originally reviewed.
3. An objection binds a revision and includes public text, severity (concern,
   major, blocking), affected constituency with provenance, and an optional
   suggested amendment. Self-described impact does not verify representation.
   Start unresolved; only the authorized proposer/delegate can append an
   accepted or declined response. Require a reason for decline and a response
   for acceptance. Acceptance links to the resulting revision/redline before
   claiming that the objection changed the proposal. Other objections remain
   visible and unresolved; popularity never silently resolves them.
4. Resolution events preserve actor, time, prior state, reason and revision link.
   Reopening is an explicit appended unresolved event. Use expected-version
   concurrency checks so two responses cannot silently replace each other.
5. A round binds one immutable revision, an immutable rule snapshot and explicit
   UTC opensAt/closesAt with opensAt < closesAt. Accept votes at opensAt <= now
   < closesAt. Freeze the window on opening; corrections require a new auditable
   round. Require revision and round IDs on every ballot mutation.
6. Ballots are unique per private participant key + revision + round. Choices
   are support, oppose, unsure, or explicit withdrawal. Support a second round
   only by deliberate organizer action and fresh participant consent. No vote
   carries forward. Keep history across replacements and withdrawal with private
   receipts, idempotency and durable-save semantics. Reject closed/stale writes
   before mutation, including retries after close unless returning an already
   recorded idempotent result.
7. Add records without rekeying legacy ballots or inventing historical windows.
   Mark existing proposals as legacy/unwindowed. Retain original votes, records,
   source IDs and receipts; any future reconciliation requires its own review.
   Retain one-writer storage until a transactional multi-writer store is ready.

## Public decision rule and denominators

Publish the rule before a round opens. Its immutable version must specify
eligibility and snapshot date, quorum value/unit, consent threshold, threshold
denominator, unsure/withdrawal treatment, window, unresolved-objection handling,
privacy suppression and advisory-only status. Changing any field creates a new
version for a future round; historical results retain their original rule.
Validate finite ranges and positive quorum; missing rules cannot open a round.
No pilot quorum or consent threshold is configured by this review.

Display support S, oppose O, unsure U, participation N=S+O+U and any separate
decisive denominator D=S+O. Withdrawals are excluded from current totals but
retained as history. Specify whether threshold uses S/N or S/D; never switch
silently. At N=0 show “No responses”; at D=0 decisive support is undefined.
Quorum counts eligible participating identities, never the number of objections
or synthetic residents. If turnout uses eligible cohort size E, freeze and cite
E; do not substitute county population. Without reliable E, label turnout unknown.
Keep open-round results provisional; report quorum unmet, advisory threshold met
or not met after closing, with unresolved objections listed separately.

Cookie identities are browser identities, not unique people. Clearing cookies
can create another identity. A bounded pilot must disclose its recruitment and
identity limitations; stronger cohort eligibility requires separate authorization
and testing. Threshold met must never be labeled governmental approval, automatic
legal action, authority to merge code or agreement by all residents.

Participant-map results must be computed only from that revision/round's eligible
responses with explicit geography consent and provenance. No participation means
“No participant data,” never agreement. Separate self-reported/unverified areas
from verified eligibility, and real data from the existing sandbox. Apply a
reviewed minimum aggregation size and suppression rule to small cells; publish
the suppression meaning without exposing private location or identity-to-choice
links. Do not infer geography from objection text or a proposal's jurisdiction.

## Pilot walkthrough and acceptance fixtures

Use an isolated temporary database and a small consenting cohort. An organizer
publishes the rule and revision 1. A participant reviews sources and votes, then
records a major accessibility objection identifying the affected constituency.
The proposer accepts it, publishes revision 2 with a ramp-access redline, and
links that change from the response timeline. Decline a separate objection with
a reason and leave a third unresolved. Open an optional second round; the same
participant explicitly votes again. Review both immutable results side by side,
including each window, rule, denominator and remaining objections. Inspect an
area with no participants and confirm it never displays agreement. End with an
advisory result and no legal, outreach, merge or deployment action.

Required implementation fixtures (specified here, not added or executed):

| Fixture | Expected result |
| --- | --- |
| R1 S=6/O=3/U=1, then R2 S=2/O=1/U=1 | N1=10, N2=4; no transferred votes. S/N is 60% and 50%; S/D is 6/9 and 2/3, labeled separately. |
| Zero responses; all unsure; below/exact quorum; threshold equality | No divide-by-zero, false consensus or implicit majority rule. Explicit comparison semantics. |
| Exact open/close timestamps and late offline submission | Server-time boundary enforcement; no local-time extension or silent retargeting to the new revision. |
| Repeat/reordered writes, save failure and restart | One current choice per scoped identity, stable retries/receipts, no false success or lost historical counts. |
| Unauthorized response, cross-proposal objection ID, stale edit | Rejected without state changes or leaking private ownership. |
| Accepted objection without published revision; declined without reason | No fabricated change link; validation blocks incomplete decisions. |
| Same IDs across repository/kind scopes; PR head/base changes | Existing repository isolation, current-head checks and records remain intact. |
| Unknown geography, tiny cell, synthetic county and withdrawn vote | No real agreement claim, private location leak or inclusion of simulation. |
| Rule change after R1; disabled optional second round | R1 unchanged; no reopening or automatic vote transfer. |
| Public text containing markup/contact details | Safe text rendering, bounded inputs and reviewed moderation/privacy path. |

Accessibility acceptance requires keyboard-only objection/response/re-vote flow,
explicit severity and constituency labels, focus recovery after errors and
publishing, screen-reader status announcements, textual redlines and map/table
alternatives, non-color status cues, 200% zoom and mobile layout. Automated DOM
checks supplement manual assistive-technology review; none is claimed here.

Before acceptance, verify the actual deployed commit and source against the
recovered tree after SHE-281, then repeat route and product walkthroughs on an
authorized staging build. Live read-only checks must identify their build and
timestamp; do not submit test ballots to production. A real consenting user must
complete the pilot while sources, privacy and advisory status remain intact.
