## Implemented

The sample-proposal `/votes` stage shows a neutral paper receipt and short stamp after the existing explicit vote button receives `{ok: true}` from `/api/votes`. Support, Oppose and Not sure share identical styling and motion. The receipt captures the submitted proposal identity, selection and viewed-text fingerprint, independently of the current selection and subsequent count refresh. Exact-choice retries retain this snapshot. Missing acknowledgement and failures do not create or animate a receipt. Earlier recovered receipts remain historical mutation status and do not animate on load.

The receipt sits outside synthetic demo tallies and explicitly distinguishes non-binding browser choices from synthetic responses, verified eligibility, turnout and official electoral authority. Change vote focuses the native voting controls without submitting. Copy receipt writes only on explicit click and reports clipboard failure with a selectable-text fallback. Controls wrap and provide 44px minimum height. CSS uses the shared motion scale and disables receipt animation in off/reduced-motion modes. This local element animation adds no global View Transition selectors or types. Public guide copy documents these limits.

## Revision limitation

The existing sample-vote endpoint acknowledges an upsert with no server revision binding. The displayed `text-…` revision is a local non-cryptographic fingerprint of proposal ID, title, current and proposed text captured at submission. It is explicitly labeled a viewed-text identifier, not a verified server revision or ballot ID. Tallies do not change that identifier. Earlier pending choices with no fingerprint say unavailable. This work preserves the API and data model; acceptance requiring an authoritative revision-bound civic vote needs separate server design. Repository PR head/base ballot binding is untouched.
