# SHE-808 — public write network failures and retries

Refs: https://linear.app/shel-bernstein/issue/SHE-808/cs-l100018-network-error-and-slow-connection-ux-for-public-write

Implemented locally for human review; acceptance remains open.

Read repository instructions, README public-write/API/privacy sections, and the
launch merge and community vote batch docs. The active journal uses
JournalSharing through /api/publish_draft; the older journal form uses /api/entries.
The /votes flow already locks synchronously, retries an exact advisory upsert,
retains an unconfirmed draft and confirms receipts only on an explicit server ack.

Journal sharing now keeps the reviewed excerpt and UUID key across explicit
retries, retains text, locks duplicate clicks, times out after 15 seconds and
observes Retry-After. Offline, timeout, 429, network errors and 5xx have distinct
copy. Advisory vote failures use the same classification. No automatic retries or
private-draft persistence were introduced. The older journal form also sends a
stable key and uses a synchronous lock and timeout.

The journal API accepts optional UUID v4 body idempotencyKey on its three aliases.
The claim is bound to the signed browser identity, endpoint and exact JSON body.
Existing validation, auth, pause controls and rate limits precede claims. Legacy
unkeyed requests retain their previous semantics. Concurrent same-key requests
share execution; successful retries read the existing entry. Deletion or hiding
prevents content replay and does not recreate a post. Private retry records store
hashes and response metadata, excluding journal text/coordinates. Reset preserves
claims. Existing entries, votes and repository governance records are retained.

Claims are saved before creation. A server crash or uncertain failure before
recording the result leaves a 409 uncertain-outcome claim. This sacrifices automatic
recovery of that attempt to prevent duplicate creation. Keep the text and check
the feed; do not claim that every interrupted attempt can be completed by retry.
The existing single-process JSON writer and durable volume remain prerequisites.
Retries still consume the existing rate-limit budget. Fork event streams remain
in memory. Page reload loses journal text and its retry key, as the form discloses.

## Existing PR overlap

Initial issue-specific and combined network/retry searches returned no matches.
A broader open-journal search found PR #327 (SHE-938):
https://github.com/adnanwahab/dear_congress/pull/327
Its diff implements a different header-based transaction/receipt mechanism for
journal and vote writes, retains full response bodies, and modifies the same
server wrapper, client helper and DB type. It is an open review candidate, not
accepted implementation. Do not independently merge both mechanisms. A maintainer
must reconcile key transport, transaction semantics, deletion/privacy lifecycle
and tests into one implementation. This local version avoids retaining submitted
journal text in receipts and explicitly blocks interrupted claims. PR #328
moderation burst work and #326 advisory tally work are adjacent scope; their
metadata was found, not accepted as behavior evidence.
