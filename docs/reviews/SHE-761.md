## Scope and protocol

The existing guided proposal workspace is the supported draft kind. Explicitly
save current edits before transferring. No scan of other localStorage records,
journals, ballots, amendments, source records or identity credentials occurs.
The sender projects the workspace envelope and known fields, preserves ID,
saved timestamp, jurisdiction and exact text, and encrypts locally with a fresh
AES-256-GCM key and 96-bit random IV. Authenticated additional data binds the
payload to `adnanwahab/dear_congress:private-workspace:v1`. Keys are never sent to
the relay. Payloads above 44 KB UTF-8 use the documented manual fallback.

POST /api/draft-handoff supports create, claim and revoke. Create accepts only
bounded encoded ciphertext and IV, returning independent random 256-bit claim
and revocation capabilities. The link carries only the claim ID in its fragment;
the key is a separate selectable field, never added to URLs or network requests.
No GET consumes a handoff. Claim is an explicit button, deleting the ciphertext
synchronously before responding. One claimant wins. Wrong keys, interrupted
responses and browser closure after claiming require a fresh handoff. Source
storage is never deleted. Revocation requires its separate capability; claim
holders cannot revoke without consuming. No public list/read API exists.

The relay uses bounded process memory (100 records, 60 KB encoded ciphertext
per record), per-record expiry timers and lazy expiry checks. It writes no file,
application database, publication, telemetry event or receipt. Expiry is 15
minutes and restart fails unavailable. As with the existing JSON-file application,
this requires one writer process; do not scale across independent workers. A
future multi-worker implementation needs a separately reviewed atomic shared
relay with TTL. Responses use existing no-store/security headers, signed browser
identity, same-origin write checks, bounded JSON and IP/browser rate limits.
Neither claim nor revocation capabilities are substitutes for voting authority.

## Recovery and accessibility

The receiver decrypts locally and reviews plain text, rendering no draft HTML.
Saving is explicit and permitted only if the destination workspace key is absent;
existing or corrupt records are retained. Blocked storage leaves the received
text selectable on the page. No source, vote, PR head/base binding or publication
permission changes. The original workspace remains the recovery copy.

Account, desktop utilities and the existing mobile More dialog expose handoff;
the guided editor links there too. Native labeled inputs, password key entry,
buttons, textarea and polite status share the same information on every device.
Inputs fit their container; buttons have 44px minimum height and visible focus.
No added animations, timers in the UI, background polling, automatic retries,
auto-claim or personalization. Reduced motion and low-power operation require no
special alternative. Shared motion/navigation/theme foundations are reused.

Fallback: keep the original page open; copy draft text through a trusted private
channel. Never publish a journal to transfer it. Keep received text before leaving.
For an expired, revoked, consumed or restart-lost handoff, ask the sender for a
new handoff and key. Revocation cannot erase copies already opened. Browser
profile users can read locally saved drafts and visible handoff credentials.
Encryption does not protect against compromised client code, browser extensions,
or a recipient sharing the key. This is not a reviewed private diary or ballot
system. Public guide, privacy page and README describe these boundaries.
