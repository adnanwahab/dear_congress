## Concrete implementation boundary

Start with transit or rent, whichever first has reviewed paired actor/event
output and aggregate provenance. Keep childcare and service access explicitly
unavailable until their mechanisms exist. The issue permits one supported domain;
it does not require fabricated coverage of all four.

Define a versioned read-only story receipt with source repository/revision,
source kind and ID, exact package/content hash or law ID, model/assumption
versions, seed, horizon, units, synthetic population definition and aggregate
metric references. Each event needs a stable event ID, synthetic household ID,
checkpoint, baseline/alternative values, named variables, units and source
references. Missing values need explicit reasons. Validate finite values,
ordered checkpoints, unique identities, supported units, matching run provenance
and paired initial state before rendering. Reject malformed or mismatched data;
do not repair missing results with illustrative numbers.

Narration must be a deterministic template over the same displayed variables.
For example, a supplied transit event may describe the recorded wait and trip
duration; it must not infer a missed shift, stress, family relationships, job,
disability or motivation. A monthly rent value must not be narrated as a daily
payment. State snapshots should be described as recorded states unless the
model actually logs the event or causal mechanism. Give exact values alongside
any rounded prose and retain event-to-source disclosures.

Offer optional, explicitly synthetic group lenses with documented assumptions,
denominators and unavailable cases. Switching lens must not change seeds or
silently imply population representativeness. Never initialize from visitor
journals, accounts, location, cookies or inferred attributes. Keep choices in
component memory; reset clears story, lens and pending work. No new persistence,
snapshot fields, external URL payloads or consent changes are needed for this
slice. Identity-bearing source payloads must not be reused wholesale.

After source binding is reviewed, put the bounded walkthrough in the selected
proposal's Outcomes stage with a return link to its original source, using the
existing proposal/topic route helpers. A `/synth` entry may reuse the component
only with an explicitly corresponding package receipt. Remount on source or
revision change; never silently reuse another proposal's story. Keep real
official records, fictional samples, synthetic outputs and browser advisory
votes visibly separate. Update public-guide copy and its contract checks with
the implementation, including privacy wording.

## Acceptance and focused verification still required

All four acceptance criteria remain pending. Required implementation checks:

- Reconcile every narrated event with exact receipt variables and provenance;
  test a supported event, adverse trade-off, unchanged value and missing metric.
  Assert that narration introduces no facts absent from the receipt.
- Exercise alternate lenses, voluntary entry, reset, source revision changes,
  invalid IDs and stale async responses. Assert no network publication, storage,
  journal inference or alteration of votes, snapshots, records or receipts.

  announcements, 390px layout and 200% zoom on the actual story surface.

  binding, with delayed response rejection after changing proposal or lens.
  Human acceptance and production-equivalent release verification remain separate.
