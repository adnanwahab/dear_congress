## Reversible off-production execution plan

This is a proposed plan for a listener-enabled environment, not an authorization
to target the public site. Keep the workload restricted to literal loopback
`127.0.0.1` with a fixed local port, redirects disabled and an egress-denied target
and generator. Fail closed on any other origin. A remote staging run requires a
separately confirmed isolated target, owner, resource/spend budget and equivalent
egress controls; never use `https://civic-synthesis.fly.dev` as a fallback.

1. Record source SHA and dirty diff, Bun/k6 versions, OS, CPU model/core quota,
   RAM limit, storage type, server and generator topology. Use a fresh temporary
   directory and environment allowlist, following smoke-routes.ts. Set DB_PATH,
   HBL_DB_PATH and STATS_DB_PATH inside that directory, NODE_ENV=production,
   OUTCOMES_MODE=off, a fresh local ANON_COOKIE_SECRET, HBL_SINGLE_WRITER=1,
   HBL_MERGE_ENABLED=0, HBL_MERGE_DRY_RUN=1 and HBL_KILL_SWITCH=1. Provide no
   service credentials, production mounts, imports or real identity records.
   Preserve the default write limits. Verify all database files resolve inside
   the temporary directory before starting. Use bundled synthetic fixtures only.
2. Start the production build in a network namespace/container published only
   on loopback. Confirm `/version` matches the recorded build, `/healthz` is
   healthy, and sample labels remain explicit. Verify one full cookie-bound
   journey manually on this target. Keep all artifacts local, with no cookie,
   journal, identity or request-body logging.
3. Implement a k6 scenario that fetches `/`, `/feed`, `/votes`, then `/api/state`.
   Validate status, content type and expected shell/state shape. Obtain an
   existing need ID from that state; for the write cohort send
   `{allocation:{[needId]:1}}` with same-origin Origin and the issued cookie,
   then reread state and assert the saved allocation. Because the cookie is
   Secure, use local TLS or explicitly replay only the server-issued cookie
   within the fixed loopback origin; never mint an identity or log the value.
   Separate request tags for each route and the post-save read. Empty needs or
   absent cookie fail preflight rather than producing fake success. No reset,
   journal, publication, repository ballot or external comment routes are used.
4. Run a 1-journey/s, 30-second warmup, excluded from reported steady-state
   latency. Use k6 arrival-rate stages: 1 journey/s for 60 seconds, linear ramp
   to 2 over 30 seconds, hold 2 for 60 seconds, return to 1 over 30 seconds,
   hold 1 for 60 seconds. Cap concurrent VUs at 10 and total duration at five
   minutes including warmup. Each journey has four reads. Cap the write cohort
   at 20 total submissions per fresh run, spread across synthetic sessions,
   plus 20 readbacks; this remains below the default IP limit. Record its
   small sample size; its p99 is not a statistically strong tail estimate.
   Do not extrapolate this bounded initial run to high-volume vote capacity.
5. Stop the generator immediately on isolation/identity mismatch, any external
   request, or target restart. Use 5-second request timeouts. Abort after the
   first 30 seconds for >1% failed journeys or p95 >2 seconds sustained over a
   30-second window; include timeouts, failed checks, 429 and 5xx as failures.
   An independent supervisor samples each second and stops at CPU >85% of its
   assigned quota or RSS >80% of its memory limit for 10 seconds, disk free
   <20%, growing write queue for 30 seconds, or generator dropped iterations
   >0. Preserve the failed run; never silently reduce load and call it a pass.
   These are proposed safety limits, not accepted product SLOs.
6. Stop the generator before the target; retain redacted metrics, then remove
   only the uniquely created temporary environment. No production rollback or
   data restore is needed. Baseline and comparison runs each use a fresh
   identical fixture and resource limits. Repeat three paired runs, alternating
   baseline/candidate order; report every run, not just the fastest. There is
   currently no candidate behavior change to compare.

## Required report and staged expansion

Export k6 per-route count, p50/p95/p99 (milliseconds), status counts, failed checks,
network errors/timeouts, achieved journeys/s, request rate, dropped iterations and
sent/received bytes and bytes/s. Include phase boundaries and raw redacted output.
Sample target and generator CPU and RSS separately every second, plus disk I/O,
free space, JSON write queue pending/active/age and process restarts. Report peak
and sustained CPU as a percentage of assigned core capacity, peak RSS in MiB,
and queue growth/drain times. Operator health exposes some queue pressure but
explicitly lacks actual DB saturation; do not label unknown telemetry healthy.
Track generator saturation separately from target saturation. HTTP bytes exclude
TLS/network overhead unless collected independently; report the distinction.

The initial bounded run is a safe baseline, not a saturation search. If clean,
review the measurements and agree the next rate/cost ceiling before expanding on
an isolated production-equivalent environment. Keep read and write curves
separate. A single-IP 429 plateau is an admission limit, not database capacity.
High-volume write testing needs an explicit staging identity/network model that
preserves real auth and limits, then a separately reviewed ramp/soak. Measure
queue growth and recovery to identify a resource knee; if none occurs within the
approved ceiling, say saturation was not reached. Do not increase the ceiling
automatically. Add browser navigation/render timings separately before making
claims about the complete public experience. Human acceptance and parity review
are required before any traffic purchase or production rollout decision.
