## Current product walkthrough from source

1. `/journal` selects the recovered `JournalScreen`; its publication is not a
   private proposal draft. The older journal conversion UI is in `App.tsx`'s
   legacy journal, so a recovered-route journey must be tested explicitly.
2. `/needs` uses the legacy needs screen. It ranks needs and sample options; it
   does not guide a person through the requested structured bill proposal.
3. `/draft` selects `WorkflowScreen`: fictional current/proposed clauses,
   illustrative summary, sample download and browser sponsor tracker. These
   clauses are not editable personal proposal text or verified legal authority.
4. `/proposals/new` selects `CitizenProposals`. It supports title, problem,
   proposed change, jurisdiction (including unsure), place and supporting text.
   A UUID draft with values and save time is stored in localStorage and resumed
   with `?draft=…`. This is device/browser storage, not encrypted storage or an
   account-backed private workspace. Preserve existing saved drafts during upgrades.
5. `?fromJournal=…` fetches a public source and retains its ID. Missing, hidden or
   pending sources are rejected server-side. Copied text remains independent;
   deleting a source must not silently rewrite an existing proposal or its votes.
6. Publication requires explicit `confirmedPublic`, a stable idempotency UUID,
   and required text fields. `publishCitizenProposal` immediately creates a
   published record with zero votes. No pending-review state exists. Costs and
   sources are optional/unstructured; affected people and benefit are absent.
7. `/proposals/:id` supports a permanent public link, discussion and advisory
   support/oppose/unsure/withdrawal. Published text is immutable. However,
   `App.tsx` explicitly selects sample `WorkflowScreen` for `/votes` and `/feed`,
   bypassing the citizen list there. An approved proposal handoff must resolve
   to that exact citizen proposal rather than a sample or repository ballot.

The current form partially covers private save/resume and shareable published
detail. It does not meet the wizard, structured output, validation, moderated
publication or integrated approved handoff requirements.

## Proposed pilot implementation contract (not implemented)

Extend the existing citizen proposal editor and shared schema rather than create
a second ballot store. Keep the current localStorage key/UUIDs readable; version
the new draft envelope and add optional fields without modifying published legacy
records. Clearly explain local-device privacy, shared-device access, storage
failure and lack of cross-device recovery. Saving or resuming must never call a
public-write endpoint. Offer deletion of a local draft without deleting a source.

Use these guided steps, with editable values preserved on back/next/save/reload:

| Step | Fields and output |
| --- | --- |
| Place/process | City, county, state or federal; named jurisdiction; process template |
| Experience | Problem, affected people, intended benefit; optional source journal ID |
| Change | Mechanism, possible enacting body, editable proposed text |
| Trade-offs | Costs/funding and uncertainty, objections and responses |
| Evidence | User-supplied source URLs, titles, what each supports, verification state |
| Review | Plain-English summary, structured sections, unresolved gaps, citizen-authored/advisory disclosure |

Templates should prompt for a city council ordinance, county governing-body
action, state legislative bill or federal congressional bill respectively. They
are drafting outlines, not assertions that a body has power in a particular
place. Require human verification of the named authority and local process.
Keep unknown jurisdiction, costs and sources visibly unresolved; permit saving
incomplete drafts but block submission until required gaps are resolved. An
explicit unknown cost must remain unknown and require reviewer attention, never
be converted to zero or an inferred catalog estimate.

Generate only editable draft suggestions. Derive the summary from supplied
content and label generated passages. Preserve original user text and provenance;
never fabricate citations, section numbers, current-law text, sponsors or legal
authority. Structured output should separate findings, scope, operative change,
implementation, costs, objections and sources. A redline needs an identified,
verified baseline plus proposed replacement; without one, label it proposed new
text and show the missing baseline instead of inventing a deletion.

Add a server-enforced review lifecycle: local draft → explicit submission consent
→ private pending moderation → approved revision → separate explicit publication
consent → published citizen-authored proposal. Consent and moderation must bind
to the exact submitted revision; edits invalidate both. Reject direct API bypasses.
Pending/rejected/hidden content must be absent from public lists, detail reads,
discussion and vote endpoints. Do not expose pending drafts through share URLs.
Extend moderation to proposal text, sources and comments; journal moderation
alone is insufficient. Coordinate withdrawal/takedown and retention disclosures.

Keep existing published proposal IDs, source IDs, response choices, comments,
idempotency keys and receipts intact. New editable draft revisions must never
rewrite already-voted text. After human approval and explicit publication, return
the existing permanent detail URL and a one-click advisory voting handoff for
that same proposal/revision. Clicking the handoff must not cast a vote. Do not
translate citizen responses into verified repository ballots or merge authority.

## Pilot acceptance fixtures and checks (planned, not executed)

Use disposable local databases and synthetic text; do not post test content to
production. Cover all four process templates and these representative cases:

| Fixture | Expected evidence |
| --- | --- |
| City late-bus problem with supplied sources and cost uncertainty | Editable summary/sections; gaps retained; save/reload preserves all text |
| County proposal with disputed authority | Reviewer sees unverified authority; no invented power or citation |
| State and federal proposals | Correct process outline, no automatic sponsor or official status |
| Empty jurisdiction/cost/sources | Field-specific errors; private save works; submission cannot silently fill values |
| Personal contact details in text or source URLs | Held privately for moderation; no public projection or vote access |
| Forged approval, stale consent, edit after approval | API rejects publication until current revision is reviewed and consented |
| Hidden/deleted source and lost cookie | No ownership reassignment; clear recovery; old proposal/source identity retained |
| Legacy draft, corrupt storage, quota denial | Existing valid draft resumes; actionable storage error; no accidental publication |
| Duplicate submit and lost successful response | Stable UUID/revision retry returns one record; differing payload conflicts |
| Two browsers, vote replacement/withdrawal and restart | Independent advisory choices persist; old tallies/records remain intact |
| Script markup, malformed/unsafe URL, oversized text | Escaped rendering, safe links and bounded server validation |
| Approved share/handoff | Exact published citizen proposal, zero automatic votes, no sample/repository mix-up |

Walk one pilot participant from journal through needs to a privately saved draft,
resume, correction, explicit review, moderation, explicit publication, share and
advisory response. Record confusion and completion evidence with permission; no
claim of representative participation or official governmental voting. Stop before
scaling until a real participant completes the flow with sources/privacy intact.

Accessibility acceptance must include keyboard-only back/next/save/review,
associated labels and instructions, error summary focus and field links, announced
save/error status, visible focus, sensible heading/step order, no color-only
validation, and narrow viewport/200% zoom. Test screen-reader announcement and
focus movement in a native browser. Source inspection or DOM assertions alone
cannot establish these criteria.
