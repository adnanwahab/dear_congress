## Implemented behavior

- Motion snapshots retain sample proposal identities/text/tallies, but strip
  browser choices and browser counts on both read (including legacy caches) and
  write. No saved server vote is deleted or migrated.
- The current page applies only its newest read. Starting a mutation invalidates
  older reads even when the write acknowledgement is lost. A failed read keeps
  the existing counts explicitly stale and hides the selected-choice highlight;
  the next successful fetch replaces counts and choice together.
- The voting page's daily question uses that same snapshot, so a second query
  cannot show a contradictory saved choice on the same page. Its homepage use
  retains the existing independent daily-question behavior.
- Browser counts remain under **Unverified browser votes — advisory**. Synthetic
  totals stay under **Synthetic demo data — illustrative**, with unchanged IDs,
  values and sample labels. Neither establishes verified people or eligibility.
- Successful snapshots show their local fetch time and warn that another browser
  may since have changed its choice. Pending/failed refreshes show **Snapshot may
  be stale**. Receipts remain historical server acknowledgements, not current
  vote authority.

## Refresh contract and cost

The workflow fetches on mount, every 30 seconds while visible, on focus, on
visibility return and on the browser online event. Automatic refresh skips an
in-flight vote. Explicit Refresh advisory counts also repairs the snapshot.
Confirmed and ambiguous writes both trigger a read. Failed writes remain retryable
through the existing exact-choice workflow; no automatic vote writes were added.
Unmount removes refresh listeners/timers and fences late responses. Responses
come from the existing no-store API. These are periodic snapshots, not a push
feed or a claim of transactionally live counts. A hidden/offline/throttled tab
has no freshness SLA; it refreshes when resumed or explicitly requested.

Periodic cost is at most two extra workflow GETs per visible minute (focus,
reconnect and user refresh can add requests); no identity telemetry is added.
LiveRound remains its separate temporary SSE round with its existing reconnect
behavior; its counts never enter the ordinary browser tally. Citizen proposal
records and the legacy citizen board/API are unchanged.

## Local reliability measurement and validation

`bun scripts/measure-advisory-consistency.ts` delivers an older read after a newer
one for 100 deterministic trials. The baseline reproduces the former unconditional
`.then(setData)` behavior. Observed stale-result regressions: **100/100 before,
0/100 after**. Network requests: **0**. This measures ordering reliability, not
production latency, throughput or real user error rates. No public load test or
production write was performed.

Focused tests cover legacy cache stripping, racing reads, mutation invalidation,
failed fetch/repair, unmount fencing, and the existing proposal/motion contracts.
The mounted UI verifier additionally checks failed post-save refresh, hidden
selection, manual repair and cross-tab withdrawal repair on focus. The HTTP
integration test now checks concurrent withdrawal/change/unsure writes, reconciles
the public tally against the persisted records, and preserves synthetic totals.

Validation results are recorded below after the final checks. HTTP tests require
a runner permitted to bind a local server; this sandbox reports EADDRINUSE even
for port 0. This limitation must be resolved before acceptance.
