## Bounded pilot design

Start after human confirmation of source alignment and SHE-283 moderation
readiness. Use one explicitly fictional, non-sensitive proposal in a disposable
pilot dataset and a small invited participant group; include supporters,
opponents and undecided readers. Do not import production votes or journals.
Use the same proposal and revision on `/published` and `/votes`, with a link
from each to its clauses and full deliberation. Expansion to citizen proposals
is a separate integration step with the same isolation contract.

Interpret “two trees” as **Reasons for** and **Concerns**. Each node can carry
**What would change my mind**, an evidence condition rather than a third vote.
A reason can have supporting claims and rebuttals; concerns can have mitigations
and replies. Allow empty sides and say “No reviewed arguments yet”; never invent
a balancing claim. Equal presentation does not imply equal evidentiary support.

Before vote controls, show one reviewed lead point per side with equal space,
source labels, strength rationale, uncertainty and clause links. Offer “Read all
arguments” and an always available advisory vote action; reading is not compelled.
On narrow screens use Reasons for then Concerns consistently, without hiding
one behind a default inactive tab. Background references stay labelled as such.

For the pilot, human reviewers select lead points using one published rubric:
clause relevance, directness and quality of evidence, disclosure of limitations,
and engagement with the strongest relevant counterargument. Record rubric
rationale, reviewer and selection version for both sides; ties use stable IDs.
Do not rank by party, ideology, author identity, popularity or vote totals. Do not
call a point “strongest” before this review. AI may suggest categories only;
label suggestions and require a human to confirm them. Neither AI output nor a
source's institutional reputation alone establishes truth or evidence strength.

## Proposed contracts and invariants

- Scope every map by source namespace, proposal kind, proposal ID and immutable
  revision digest. Use stable clause IDs with quoted text plus that digest;
  reject stale or unknown anchors instead of attaching them to similar text.
  Demo catalog, citizen proposals and repository items must not collide. Any
  future repository PR integration additionally binds repository ID, kind,
  PR number, head SHA and base SHA; issue priority remains a separate kind.
- Store argument IDs, side, parent ID, claim text, clause anchor, limitations and
  change-mind condition. Reject cross-map parents, cycles and excessive depth;
  bound text, source counts and request size. Persist maps additively in the
  existing single-writer model without rewriting existing records or ballots.
- Each evidence claim renders either a source with title, author/publisher,
  publication date when known, URL and passage/page locator, or the literal
  **unverified assertion** marker. A rationale links strength to the claim:
  unassessed, limited, moderate or strong. Source supplied is not source verified;
  display disputed, unavailable and retracted status independently of strength.
  Value judgments should be labelled, not assigned fabricated empirical proof.
- Validate outbound URLs to HTTP/HTTPS, render contributed text safely and use
  safe external-link attributes. Do not fetch submitted URLs server-side in the
  pilot; this avoids introducing arbitrary-network retrieval and tracking previews.
  Record provenance without copying whole copyrighted documents or private data.
- Corrections append a target argument/citation ID, explanation, proposed corrected
  text and source or unverified marker. Keep original revisions and public
  disposition (pending, accepted, declined with rationale); acceptance creates a
  new visible revision, never a silent edit or automatic change to ballots.
- Reports target a specific argument, citation or correction with a reason and
  private reporter identity. Deduplicate retries, limit abuse, check existing
  cookie/origin/auth boundaries and avoid exposing identity hashes or reports.
  A report alone does not establish misleading content or hide an opposing view.
- Extend the established moderator boundary to these new content kinds, failing
  closed without configuration. A hide action requires an authenticated moderator
  and reason, appends an audit event and returns a tombstone with safe public reason.
  Keep abusive text out of public projections; retain restricted original evidence.
  Do not expose personal data in public hide reasons. Hide/show never touches
  vote stores, tally calculations, revision bindings or historical receipts.
- Separate deliberation permissions/storage from all voting executors. Corrections,
  lead selection, reports and moderation create zero votes and zero merge authority.
  Keep publication consent, privacy deletion rules, idempotency and atomic persistence.
  Do not claim anonymous browser cookies establish verified resident identity.

## Required walkthrough and fixture plan (not executed)

A facilitator opens the pilot from `/published`, selects a clause, follows a
source passage, and compares the lead pro/con points on `/votes`. A participant
opens a rebuttal, adds a reasoned correction and flags a misleading citation.
A moderator hides an abusive reply with a reason. The participant then casts,
changes and withdraws an advisory vote. Compare persisted ballots/totals before
and after each non-voting action, reload and restart, and confirm the correction
history and moderation tombstone remain visible without exposing private reports.

| Fixture | Required observation |
| --- | --- |
| One sourced pro, one sourced con, one unsourced empirical claim | Same visual treatment; exact source/locator or unverified marker on every claim |
| Credible source irrelevant to the claim; conflicting studies; dead/retracted URL | Limits and dispute state visible; no automatic strong rating |
| Single-side/empty map and equal rubric scores | Honest empty state and stable selection; no fabricated balance |
| Correction accepted/declined, duplicate retry, concurrent report | Original retained, reasoned disposition, no duplicates or lost writes |
| Abuse, personal information, script text, unsafe URL | Safe rendering, private reports, authorized hide, no vote delta |
| Unauthorized moderator, cross-origin write, forged browser ID | Existing auth/origin/rate boundaries retained; no mutation |
| Same ID across demo/citizen/repository/kind; stale revision; changed PR head/base | No cross-scope content or ballot reuse; stale mutations rejected |
| Parent cycle, deep tree, oversized claim, missing clause | Bounded validation errors and no partial writes |
| Restart, save failure, demo reset, privacy deletion | Atomic persistence and required retention; public deletion tombstone without private text |

Accessibility acceptance must include keyboard-only source/expand/report/correction
flows, visible focus, semantic headings and nested lists, labelled errors and
status announcements, and focus restoration after dialogs. Verify a screen reader
can distinguish sides, sources, evidence status and hidden-content tombstones.
At 320 CSS pixels and 200% zoom, both lead points and vote controls must remain
readable without horizontal scrolling; do not convey side/strength by color alone.
These are planned checks, not a claim of passing accessibility review.

Viewpoint-neutral review requires human review of paired examples with viewpoints
and ordering swapped. Apply the same rubric, moderation thresholds, space, type,
controls and uncertainty labels. Record disagreements and resolve inconsistent
treatment before a pilot proceeds. Collect the real participant's ability to
identify both arguments and uncertainties, use a source and submit a correction;
do not use a shift in support as the success metric. Avoid collecting political
profiles or public participant identifiers for measurement.
