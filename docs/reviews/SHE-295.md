## Current behavior and gaps

- `App.tsx` routes `/` to Dashboard and `/feed` to WorkflowScreen. The older
  citizen-proposal module documentation does not describe this recovered routing.
  Do not assume its independent search UI covers either target route.
- Dashboard searches title, summary and jurisdiction; WorkflowScreen also searches
  source. Both use local case-insensitive substring filtering intersected with
  topic. Their scope differs and is not explained beside the controls.
- Dashboard shows the matching item count but no unfiltered denominator. Feed
  displays zero items before loading completes. Neither implements the requested
  “Showing X of Y proposals” wording or highlights matches.
- Dashboard has a zero-result message and Clear filters button. Feed has a message
  without reset. Neither provides a persistent clear-all control or explicit
  submit/Escape handling.
- Query/topic initialize to defaults and are absent from URL state. Only proposal
  selection reads the URL. WorkflowScreen.choose replaces the URL with its route
  helper, so adding search URL state alone would lose it on selection.
- Filtering is already local: typing does not request the API. Dashboard refreshes
  `/api/demo` once per minute when visible; WorkflowScreen loads on mount/request
  dependency. Preserve this property.
- Both catch load failures and offer retry. Dashboard retains previously loaded
  data, but initial failure still leaves loading presentation. Empty, loading,
  failed-first-load and stale-data states need explicit distinction.
- Existing styles stack filter controls on narrow screens, but this does not
  establish keyboard accessibility, touch usability or absence of overflow.

## Implementation handoff after the gate

1. Share pure matching/count logic and filter controls between the two target
   screens. Define the scope as title, summary, source and jurisdiction, explain it
   visibly, and retain topic as a separate intersection. Count matching proposals
   against all proposals in the successfully loaded payload; label sample data
   beside counts. Never treat proposal counts as participation or official status.
2. Add a visible clear-all action and an explained zero-result state with a
   **Reset filters** button. Announce count changes politely. Show loading before
   successful data, a retryable initial failure, and stale-data feedback separately.
3. Use `q` and `topic` URL parameters, preserve `proposal`, unrelated parameters
   and hash, and restore state on back/forward. Preserve filters when choosing a
   proposal. Define unknown-topic recovery without silently showing a different
   topic. Reset only the search/topic parameters.
4. Keep filtering local. Use an accessible search form: Enter submits without page
   reload or API traffic; Escape clears search and retains focus. Clear-all/reset
   clears both filters. Highlight literal matches with React text nodes and `mark`,
   never HTML injection or an unescaped regular expression. Display a summary
   match when the title alone cannot explain why a result matched.
5. Add shared logic and DOM regressions for search-only/topic-only/intersection,
   empty payload, no matches, mixed case, literal punctuation, safe rendering,
   loading/failure/retry, stale refresh, reset, URL reload/history and selection.
   Assert typing/Enter/Escape do not trigger network requests.
6. Run `bun test`, `bun run typecheck`, and `bun run test:routes`. Exercise both
   routes in a real browser at desktop and 390px: Tab order, Enter, Escape, reset
   focus, long query/topic text, count announcements, highlighting, no horizontal
   overflow, slow API, rejected API, retry and refresh failure. Use isolated local
   fixtures for failures; live route reads require the human-reviewed release.
