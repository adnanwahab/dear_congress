## Proposed implementation contract

These are proposed requirements, not existing APIs.

1. Add an independent versioned evidence-request collection. Each task binds the
   repository, source kind, immutable proposal ID and text revision/digest, claim
   ID and exact claim excerpt. Record one bounded question, rationale for the
   gap, required source type, inclusive date interval and named jurisdiction.
   Reject inverted dates and missing bounds. Distinguish unknown dates and
   jurisdiction from a wildcard. Do not infer locality from journal text.
2. A task might ask: “What was scheduled versus observed weekday evening bus
   frequency on this named route in Houston between January and June 2026?”
   Require the operator's route-level service report, reporting period and table
   locator. This is an authored illustration, not a real request or finding.
   Separate evidence supporting, contradicting or failing to resolve a claim.
3. Store submissions separately: task/revision, source title, publisher, URL,
   publication date, covered interval/jurisdiction, locator, relevant excerpt,
   contributor explanation and declared provenance. URLs are references, never
   automatically fetched. Validate bounded input and safe link protocols; render
   user content as escaped text. A source outside task bounds requires explicit
   review rather than silently satisfying the request.
4. Default artifacts to personal. Show Public, Invite-only and Personal as text
   beside each artifact and before submission. A task's audience does not grant
   permission to publish a submission. Freeze the exact content, audience,
   source revision and consent version for review; any edit invalidates consent.
   Require separate, deliberate consent to share into a topic hub or live round.
5. Enforce ownership and artifact grants server-side on details, lists, search,
   export, topic aggregation and live streams. Invitation acceptance grants only
   its named artifacts. Deny guessed IDs, cross-repository/source-kind bindings,
   revoked grants and expired sessions. Keep credentials, grants, pending private
   content and retry hashes out of public projections; use no-store responses.
   Coordinate this contract with SHE-709 rather than treating its draft as built.
6. Submission creates a private pending moderator record and receipt, never an
   immediately public comment. A scoped moderator can request clarification,
   reject or approve with a reason. Approval cannot broaden the contributor's
   consent. Clearly label “reviewed for relevance” separately from verified truth.
   Order by explicit date/status with deterministic ID ties. Do not introduce
   likes, popularity-based truth scores, contributor leaderboards or vote-derived
   factual authority. A moderator must be able to leave a claim unresolved.
7. Append private audit events for submission, consent, review, sharing, reporting,
   leave and revocation, with actor capability, artifact/content revision, grant
   version, time and reason. Preserve source IDs and prior decisions. Separate
   minimal audit metadata from private text; define retention and backup limits
   before promising deletion. Public history must not expose withdrawn excerpts.
8. Support participant leave and owner revoke. Recheck access before every write,
   read and stream update; terminate revoked subscriptions and remove restricted
   cached UI data. Explain that already downloaded public copies cannot be
   recalled. Reporting returns a private receipt tied to artifact kind/revision;
   report text and reporter identity never become public or automatically rank
   or hide evidence. Extend moderation with typed targets without breaking the
   existing journal route.
9. Use stable operation IDs and expected record/grant versions. Same-content
   retries reconcile an uncertain result; changed-content reuse conflicts.
   Reject stale moderation and consent writes before saving/fanout. Serialize
   persistence and roll back on failed saves. Additive storage must survive
   restart and demo reset without altering existing proposals, ballots, source
   journals, PR head/base bindings, records or receipts.

## Integration and acceptance work

Citizen proposal detail should host the claim-specific board and source/revision
context. Topic hubs should aggregate only explicitly shared approved artifacts,
retaining the original claim and source links. LiveRound should link to that same
authorized artifact, not copy evidence into ephemeral vote snapshots. A live-round
code must never unlock a restricted request. Keep evidence independent of round
expiry, advisory totals and repository merge eligibility.

Do not manufacture attendees or messages to populate an empty board. Sample
tasks/contributors require persistent synthetic markers on records and every
projection. Existing temporary round totals count browser choices, not verified
people. Fictional topic samples and simulated outcomes cannot become submissions
from real contributors or verified evidence.

Acceptance requires all of the following in disposable local data:

- Complete request creation with source/date/jurisdiction bounds; submit evidence,
  receive a pending receipt, moderate with a reason, inspect approved provenance,
  and retain unresolved/contradictory sources without popularity ranking.
- Test owner, invitee, outsider and moderator for every action and projection;
  exercise permission denial, guessed IDs, wrong source kind/repository, expired
  invitations, lost cookies, leave and revoke. Assert private sentinel text is
  absent from public responses, logs, exports, topic hubs and streams.
- Change task text, content or audience after consent; revoke during an open
  form/stream; switch proposals while a request is pending; send concurrent review
  decisions; retry after a lost response; simulate save failure/restart. Expect
  conflict/denial and preserve earlier records, receipts and unrelated votes.
- Exercise empty queues, malformed links, oversized excerpts, unsupported source
  dates and script markup. Compare pre/post snapshots of existing civic ballots,
  verified repository ballots and PR head/base revisions for no changes.
- Verify keyboard-only operation, labels, heading order, status/error announcements,
  error focus and screen-reader source context. Check 390px mobile, 200% zoom,
  contrast and long URLs/excerpts. Scope and moderation state must use text.
- Run `bun test`, `bun run typecheck`, `bun run test:routes` and focused API/DOM
  journeys. Native accessibility/mobile and stale-session/privacy acceptance for
  the new feature remain unperformed; baseline tests cannot establish them.

No live app walkthrough or release-parity verification was performed. Pre-existing
worktree screenshots cover other routes and were left untouched; they are not
evidence-board acceptance. No production data or external messages were written.
