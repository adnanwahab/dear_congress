# SHE-400 — Personal priority allocation

Refs: https://linear.app/shel-bernstein/issue/SHE-400/joytouch-drag-priority-tokens-into-a-personal-100-point-allocation

## Audit and implementation

The active `/votes` and `/vote` routes render `WorkflowScreen`, rather than the
legacy `VoteView` in App.tsx. The legacy sliders therefore were not a suitable
integration point. GitHub PR searches for SHE-400 returned no existing PR;
priority search returned PR #1 (repository voting), which is a separate scope.
The GitHub CLI had no network connection; connected GitHub search was used.

Added a separately loaded personal-priority panel to the active Votes stage.
It shows 100 individual point marks across remaining/need trays, live allocated
and remaining counts, numeric inputs, labeled increment/decrement buttons,
one-point pointer dragging, Undo and explicit Save priorities. Pointer capture
handles touch/pen/mouse and cancellation does not change the draft. The panel
opts out of stage swipes; scrolling remains native outside drag trays. No new
animation or View Transition type is introduced. Existing route transitions stay
unchanged. Empty needs and loading/failure states cannot submit an allocation.

Reads use `/api/state`; the existing cookie-bound allocation persists through
`/api/votes`. Only the allocation field is sent, after explicit Save priorities;
there is no automatic save, vote, publication or retry. Save failures retain the
draft. Controls are locked during saves. Reload restores server values for the
same browser identity; unsaved edits are lost on reload. Personal priority UI
is separate from synthetic proposal responses and explains its advisory scope.
The guide and README document these semantics. Existing legacy behavior is
unchanged. No data migrations, records, repository identities or vote bindings
were changed.

## Validation and remaining acceptance

Focused interaction tests cover exact token counts, budget conservation,
overspending, numeric edits, keyboard-operable buttons, Undo, synthetic touch
pointer events, failed/explicit saves, remounting persisted values, loading,
empty catalog and absence of animation. Workflow regression fixtures now supply
personal-state reads separately from demo responses; their no-write-on-browsing
checks remain intact.

`bun run typecheck` passed. `bun run test:routes` could not start its isolated
server: Bun reports `EADDRINUSE` for port 0 in this environment. Full-suite
results are recorded below. Automated DOM tests do not establish human acceptance.
Actual device touch dragging, browser visual layout, and screen-reader journeys
still need human verification; no live endpoint was used to test participation.

## Governance retained

No merge/deployment/authentication/check configuration changed. The existing
configured source defaults remain disabled/dry-run, quorum 10, 24-hour exposure,
one current-head approval, empty base/check allowlists, active kill switch and
9 AM America/Chicago scheduling. Browser choices never become verified GitHub
merge authority. These defaults do not establish the live environment settings.
`docs/launch-merge-policy.md` still requires checks `bun test`, `bun run typecheck`
and `route smoke test`, at least one human approval, and a human-published tagged
release for production. No PR, external message, issue transition, merge,
auto-merge, release, deploy or production-data change was performed. Leave the
Linear issue open for human acceptance.

Final run: `bun test` reported **479 passed, 26 failed** across 505 tests.
The remaining failures are server-start integration tests reporting the same
port-0 `EADDRINUSE` error; the route smoke test hits that error too. The focused
allocator run passed **4/4**, and the affected workflow regression run passed
**13/13** before the additional motion check. Typecheck and `git diff --check`
passed. Required server checks must be rerun in an environment that permits
binding the isolated test server before this is eligible for merge review.
