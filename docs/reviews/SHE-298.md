## Retry contract needed before implementation

`/api/votes` upserts explicit choices for the signed cookie identity and awaits
`save()` before `{ ok: true }`. Capture the exact target and payload for retry;
do not recompute a toggle against refreshed state or apply it to a newly selected
proposal. Preserve proposal/revision, repository and item-kind isolation.

Journal creation aliases and `/api/answers` lack durable civic request-key
deduplication. A timeout or disconnected response can occur after persistence;
it cannot honestly mean “not saved.” Blind retry can create another entry/answer.
Existing citizen-proposal and verified repository feedback idempotency contracts
are separate and must not be repurposed or weakened.

After the prerequisite gate, implement a shared status component and request
controller with a synchronous duplicate lock, bounded timeout and structured
errors. Separate write acknowledgement from subsequent feed-refresh failures.
Keep confirmed receipts visible; show an entry ID for published/held entries,
and distinguish held-for-review from public publication. Treat network/500/timeout
outcomes as unconfirmed unless reconciled; use “We could not confirm whether this
was saved,” not an unsupported claim that nothing was saved. Show rate-limit wait
guidance from Retry-After without automatic resubmission.

Safe creation retries require an atomic, durable receipt keyed by signed identity,
operation and stable request key, bound to the original payload. Concurrent repeats
and restart must return the original receipt; changed payload reuse must conflict.
Retain original records, source identities and existing receipts. Review privacy
before adding browser storage: a recoverable public-composer draft must be separate
from private VisionBoard drafts, with explicit retention/clear behavior and no
automatic upload. Reconfirm public consent after reload. Do not persist sensitive
text casually or silently claim recovery when storage is unavailable.

### Implemented behavior

- A shared accessible mutation status component supports idle, submitting,
  confirmed and failed/retry states. The API helper retains HTTP status and
  Retry-After in an Error subclass and accepts an optional AbortSignal.
- A synchronous controller lock prevents duplicate pending writes, including two
  activations before React renders. Proposal browsing stays available while the
  vote buttons are pending. The payload captures the original proposal and
  explicit stance; retries never recompute a toggle from current selection.
- A 15-second transport abort ends an unconfirmed request. HTTP/network failures,
  timeout and missing `{ ok: true }` acknowledgement explicitly say the save could
  not be confirmed. They never assert that the server saved nothing. 429 explains
  when to retry using Retry-After (seconds or HTTP date); the controller blocks
  submissions until then. It never automatically resubmits.
- Confirmation requires the existing server's post-save `{ ok: true }` response.
  The visible acknowledgement identifies the proposal, stance and non-binding
  status. A subsequent failed GET has a separate refresh error and cannot turn
  the acknowledgement into a failed mutation or expose a write-retry button.
- The last exact choice and acknowledgement are retained in tab session storage,
  replacing the prior slot on a new attempt. Reloaded pending work is explicitly
  unconfirmed and offers an exact retry; a restored acknowledgement is labelled
  historical, since another tab may have changed the current choice. No reload
  sends a POST. Blocked storage is surfaced rather than claiming recovery. Closing
  the tab normally clears this storage; no journal/private draft text is stored.

The retry contract is limited to `/api/votes`' existing signed-cookie advisory
upsert. Repeating the same proposal/stance replaces that identity's choice rather
than appending a ballot. This is not a new durable server receipt ledger or an
identity guarantee. Clearing/replacing the anonymous cookie changes that identity;
concurrent tabs or requests still use the existing last-write-wins semantics.
Aborting transport does not establish that the server rolled back. The local
acknowledgement is not a signed proof or official election receipt. Existing
server validation, rate limiting, identity and persistence code is untouched.
