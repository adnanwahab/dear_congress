# SHE-396 — recorded proposal lifecycle audit

Refs: https://linear.app/shel-bernstein/issue/SHE-396/joymotion-animate-proposal-lifecycle-as-a-continuous-object

## Disposition

Analysis only, against `1305bc091550425a7c6b6038ce8afd3f6acf4d4f` on November 14, 2026.
The requested real draft → review → advisory vote → sponsor → outcome lifecycle
is not represented by the current data contract. No animation is implemented and
no acceptance criterion is claimed complete. Keep the issue open for human
verification. This report does not require permission to continue authorized
implementation; it identifies the missing source records needed to implement it
without inventing civic progress.

## Source audit

- `src/client/WorkflowScreen.tsx` reads `/api/demo`, not a real proposal lifecycle.
  `readTracker` supplies fictional fallback cards; `prepare` saves browser-local
  cards. The next-stage anchor changes routes, not recorded proposal status.
- `src/engine/demo.ts` defines fictional `DemoItem` scenarios, possible office
  categories and illustrative tallies. `updatedAt` is generated from the current
  day, not a proposal transition timestamp. Browser advisory counts are separate.
- `src/client/SponsorBoard.tsx` permits manual simulated stage selection, including
  “Introduced or offered.” Its card has only current stage and a display string;
  it does not retain an event history or establish sponsorship/introduction.
- `src/shared/civic-stages.ts` defines navigation order and editorial timing copy.
  Its six routes are not the issue's five recorded lifecycle states.
- `src/shared/citizen-proposals.ts` exposes only `status: "published"`, publication
  timestamps, comments, objections and current advisory choices. The server stores
  choices by browser hash without a vote-event timestamp/history. Publication
  immediately makes the proposal available for advisory voting; there is no
  review-completed state, sponsor evidence, official introduction or outcome record.
- `docs/citizen-proposals.md` explicitly describes private drafting, immediate
  publication, immutable published text and missing moderation lifecycle. Private
  workspace/amendment snapshots must not be silently promoted to public events.
- `src/client/proposal-motion.ts`, `view-transitions.ts` and `motion.ts` provide
  shared-title identities, route direction and typed transitions. These are visual
  tools, not evidence of lifecycle progress. Cached demo snapshots are not authority.

## Concrete implementation requirements

1. Establish an authoritative, read-only public lifecycle projection for one source
   kind and immutable proposal/revision identity. Each event needs a stable ID,
   recorded timestamp, stage, provenance/evidence reference and verification label.
   Define who may record review, sponsor and outcome evidence before adding any
   write path. Do not derive these events from visits, elapsed time, download,
   vote totals, comments, possible offices or simulated tracker moves.
2. Preserve existing records without backfilling invented history. Existing citizen
   publication can be shown with its actual timestamp; absent stages say “No
   recorded event.” Current votes are a current advisory snapshot, not a dated
   voting history. A correction/reversal must retain the prior event and evidence.
3. Render a semantic ordered timeline first, with exact dates, source links,
   explicit advisory/verification wording and persistent proposal identity. Show
   unknown and missing stages honestly. Print must retain every event and label.
4. Add one decorative glyph beside the active recorded-stage header. Key its
   transition name by source kind, proposal and revision. Move it only when a
   successful authoritative refresh supplies a new event for that same identity;
   initial loading, cached snapshots, route visits and selection changes do not
   replay stage advancement. Never morph a sample into a citizen/official record.
5. Extend the typed motion helper with a scoped lifecycle type, scaled duration
   and existing off/reduced-motion/unsupported fallbacks. Keep source status and
   timeline updates independent of animation completion. Navigation remains native
   links; no animation control submits, publishes, contacts offices or votes.

## Required verification before acceptance

Use disposable local records only. Test initial load, empty/missing history,
failed refresh/retry, duplicate events, out-of-order responses, source/revision
switching and recorded correction/reversal. A new confirmed event must move the
same glyph once; a route visit or unchanged refresh must not advance it. Verify
that private drafts, demo tallies and simulated sponsor/outcome cards cannot enter
the real timeline. Verify viewing and navigation issue no mutation requests.

Test keyboard and touch navigation, focus retention, narrow layout, static print,
reduced motion, motion off/slow, unsupported and callback-only View Transitions.
Screen readers must receive meaningful text without announcing decorative motion.
Run `bun test`, `bun run typecheck`, `bun run test:routes`; native browser and
assistive-technology checks remain necessary beyond DOM fixtures.
