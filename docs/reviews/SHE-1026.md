## Acceptance and behavior

An isolated HFL-021 fixture uses explicitly test-configured credentials for four
category reviewers and a fifth publisher. Public suggestions persist as pending;
they never supply an approval. All categories, exact digest and jurisdiction,
latest append-only decisions, configured roles and active identities are checked.
The publisher receipt binds the four IDs; any subsequent decision invalidates it.
Ordering uses insertion order, so a clock rollback cannot hide a newer revocation.
The receipt's audit actor must match its publisher identity.

The fixture advances through authenticated decisions, publisher readiness and a
separate same-origin authenticated ballot-publication action. Exact retries retain
the same publication ID, audit and immutable source/review snapshots. Changes to
windows or review snapshots conflict. Restart preserves reviews, suggestions,
publications, advisory votes and draft choices without transferring draft feedback
into ballots. Removing a configured reviewer, required role or publisher closes
readiness and ballot writes while preserving historical choices and receipts.

All 100 unreviewed originals are blocked in the isolated fixture before approvals.
No genuine approvals or production credentials were added. HFL-051 stays blocked
at both readiness and ballot publication: its separate legislative supplement has
no authenticated revision-specific review binding. Supporting publication of that
supplement requires a separately reviewed binding design; the catalog digest
alone is deliberately insufficient.

## Production credentials, volume and rollback

An operator must issue independent random 32+ character bearer credentials via
`CATALOG_REVIEWERS` in the secret manager, with stable reviewer IDs and appropriate
legal/evidence/fiscal/editorial roles and an independently assigned publisher.
No secrets belong in Git, browser storage, logs, issue bodies or this document.
A token authenticates the operator-configured identity; human qualification and
identity checks remain the administrator's responsibility. Current configuration
is authoritative for roles; retained reviewer_roles rows are historical and do
not restore removed configuration. Remove a reviewer or role from configuration
to revoke authorization durably across restarts. Direct active=0 changes alone
are durable revocations: startup preserves inactive identities, including during token refresh. Explicit operator restoration remains a separately authorized action.

Set `CATALOG_REVIEW_DB` explicitly to a separate persistent SQLite path on the
mounted volume, e.g. `/data/catalog-review.sqlite`; do not point it at the JSON,
HBL or ballot database. Without the explicit path, DB_PATH selects
`${DB_PATH}.catalog-review.sqlite`, otherwise production defaults to
`/data/catalog-review.sqlite`. Also persist `CATALOG_DB_PATH` and retain the stable
32+ character `ANON_COOKIE_SECRET`. The existing ADMIN_TOKEN plus
CATALOG_PUBLISHER_ID publication route remains separately authenticated and
cannot bypass readiness. Neither publication path trusts a JSON publisher ID.

This remains a single-writer SQLite pilot. Back up both isolated databases using
SQLite online backup or with writes stopped, preserving a consistent WAL state;
verify restoration in an isolated environment. Do not copy a live main file alone.
Rollback must retain all revision, decision, audit, receipt and vote history.
Prefer a prior compatible image that preserves these checks; reverting to code
without current reviewer revalidation is a security downgrade and needs explicit
human security assessment. Stop publication writes during such an assessment;
never reset or overwrite participation data. New append-only publication triggers
are compatible with the existing insert-only publisher path.
