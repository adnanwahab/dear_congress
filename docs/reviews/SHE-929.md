## Actual storage and risks

Advisory POST /api/votes and POST /api/journal mutate one process-local object.
Each save synchronously stringifies the entire DB, queues mkdir/write of a complete
snapshot, then atomically renames a process-specific temporary file. The queue
preserves snapshot order and recovers after write failures, but is unbounded.
In-flight requests can retain one full serialized snapshot each. A larger pool
cannot parallelize this writer. There is no advisory DB connection pool:
connection exhaustion is **not applicable**, not measured as zero. Separate launch
metrics use SQLite after saves and are included in handler timing; governance has
its own separate SQLite store. Neither should be conflated with advisory JSON.

Journal extraction and buildContext/validation also precede persistence; configured
remote LLM latency could dominate in production. This run intentionally removes
all provider credentials and uses the fallback extractor. Measurements demonstrate
queue pressure and size sensitivity, not a CPU/disk/provider attribution profile.
Multiple processes writing the same JSON would risk lost updates; retain the
single writer. Atomic rename is not a power-loss/fsync durability guarantee.
A client timeout does not cancel an accepted mutation; do not automatically retry
journals without the separately reviewed idempotency work. Current save failures
can leave an in-memory mutation whose outcome is uncertain.

## Safe staged experiment and reproduction

Run `bun --no-env-file scripts/benchmark-advisory-writes.ts` after
`bun install --frozen-lockfile`. It emits JSON to stdout. No target URL, database
path or arbitrary load controls are accepted. Each fixed case runs in a fresh
child with an environment allowlist, fresh anonymous secret, disposable JSON,
stats and governance paths, no service credentials, merges disabled/dry-run and
kill switch active. Public validation, rate limits and auth remain in place:
48 calls per fresh process stay under the default 60/IP budget. Fresh anonymous
identities are synthetic browser identifiers, never inferred verified people.

Socket binding was attempted and rejected here with EADDRINUSE on port 0.
The retained harness therefore captures Bun.serve's registered real handlers in
its child process and invokes the existing security/validation/metrics wrappers
with synthetic Request objects and a loopback peer. **No listener is opened and
no HTTP request is sent**, including to the public site. Timings include wrapped
handler execution, body decoding, extraction, stats and disk save; they exclude
TCP/TLS, proxy queues and browser transport. Bun.serve is restored immediately
after module initialization. This interception is test-only, never runtime code.

Each case has 24 journal submissions and 24 votes, with a bounded worker pool
of 16 (baseline) or 4 (mitigation experiment), 10-second call deadlines and a
120-second child watchdog. Fixture sizes are 500 and 5,000 explicitly simulated
journals. Submitted journal text says synthetic benchmark; the /api/journal
route still marks new records real in this disposable store. Its private stats
are deleted with it and never displayed as public participation. No production
records, identities, coordinates, ballots or receipts are read/copied.

The harness asserts all 48 statuses are 200, every acknowledged journal ID exists
on disk, exactly 24 independent vote maps contain the submitted vote, and every
original fixture record is unchanged. It stops its server stub and recursively
removes disposable files in finally. A hard process kill can bypass finally; an
operator should remove only that run's dc-advisory-bench-* temporary directory
if a watchdog fires. Request deadlines diagnose stalls and do not undo mutations.

## Before/after results

Raw environment and measurements: ../evidence/she-929-advisory-writes.json.
Bun 1.4.2, macOS arm64, Apple M4; one short run per cell, 24 samples per endpoint.
These are local staged observations, not a sustained capacity/SLO estimate.
p99 is effectively the maximum of 24 samples.

| Synthetic starting entries | Pool | Vote p50 / p95 / p99 ms | Journal p50 / p95 / p99 ms | Calls/sec | Sampled max pending saves |
|---|---:|---:|---:|---:|---:|
| 500 | 16 baseline | 64.04 / 97.16 / 100.98 | 63.99 / 130.84 / 135.19 | 227.35 | 16 |
| 500 | 4 bounded | 18.18 / 25.31 / 31.25 | 17.24 / 35.31 / 39.56 | 213.71 | 4 |
| 5,000 | 16 baseline | 119.54 / 135.81 / 142.02 | 128.16 / 198.17 / 206.37 | 124.07 | 16 |
| 5,000 | 4 bounded | 29.58 / 34.81 / 41.71 | 29.51 / 50.11 / 58.40 | 130.15 | 4 |

Final JSON sizes: 333,090 and 3,145,090 bytes. All four cases: 48/48 HTTP-style
200 handler responses; zero 409 conflicts (0/48), 429s, 5xx, client errors/timeouts
or acknowledged-record losses. No connection-pool exhaustion can occur in the
advisory JSON store. These independent-identity cases do **not** test same-browser
revision races, lost responses/retries, process crashes, disk-full errors or
multiple writers. A zero 409 rate does not establish conflict protection.
Queue depth is sampled via authenticated operator health about every 5 ms;
event-loop delay can miss peaks. It is not a complete queue residence profile.

At 5,000 entries, pool 4 reduced vote p95 by 74% and journal p95 by 75%, with
roughly comparable throughput. Increasing state tenfold also lowered throughput
in both pools. This is evidence against increasing concurrency as the first
mitigation. It does not distinguish stringify, context building and disk costs.

## Reversible rollout recommendation — not executed

1. Keep one writer and existing security/rate limits. Repeat this matrix with
   multiple repetitions, larger synthetic state and independently profiled
   stringify, queue wait, disk rename and context/extraction timings. Capture
   memory/event-loop delay. Rebase and repeat after #327/#330 review.
2. In a dedicated socket-capable staging instance with its own synthetic volume,
   provider credentials disabled and no public participation exposure, run the
   same bounded HTTP matrix: begin pool 1, then 4, then at most 16, 48 calls/stage,
   10-second request deadline and 120-second overall stop. Stop on any lost record,
   timeout, write failure, unexpected 5xx or sustained rising queue. Verify restart
   readback and cleanup of the entire synthetic volume. Include an unchanged
   sentinel vote, source/proposal IDs and separate governance data in that test.
3. Prototype a configurable admission gate **before mutation/extraction**, with a
   bounded waiting queue and deadline; begin at 4 admitted writes only as an
   experimental setting. Return truthful 429/Retry-After for requests rejected
   before mutation, coordinated with #330. Never reject merely after save has
   queued or acknowledge before durable save completes. Re-run the baseline and
   mitigated matrix; require zero acknowledged loss and non-regressing throughput,
   with p95 under a proposed local 100 ms budget for this exact fallback fixture.
   A separate provider-enabled staging budget needs operator agreement.
4. Review failure atomicity, retry semantics and receipt growth with #327 before
   enabling admission in a release. A capped pool here is a load-generator
   mitigation experiment, **not an implemented fleet-wide server admission cap**.
   Client-only limits cannot bound multiple clients. Defer database migration until
   profiling separates costs; transactional storage is a candidate if snapshot
   amplification dominates, with an isolated migration/restore rehearsal first.
5. Human maintainer reviews current revision and all required checks, then decides
   on any human-published tagged release. Rollback a staging admission experiment
   by restoring its previous setting/revision after draining accepted writes,
   preserving data and receipts. No public load test, rollout or deployment is
   authorized by this report. A future public test needs an explicit safe plan.

## Validation and acceptance limits

The four-case staged handler benchmark passed all persistence assertions.
`bun run typecheck` passed; a separate strict tsc invocation including the new
script also passed (scripts are not generally in the repository tsconfig).
`bun test`: 664 passed, 26 failed, 690 total, 127,261 assertions. All 26
failures occurred in socket-dependent tests at server startup with EADDRINUSE
(including the child readiness failure in server.routes.spec.test.ts).
`bun run test:routes`: failed at the same port-0 bind before route assertions.
The in-process benchmark does not replace these required checks; rerun them in
a socket-capable runner before acceptance. `git diff --check` passed for tracked
changes; the added files were also inspected for whitespace.

Acceptance remains pending a socket-capable staging HTTP test, repeated profiling,
reviewed server-side admission/failure behavior, and human verification. This is
a measurement/review candidate, not completed production hardening.
