## Concrete findings and bounded follow-up

1. `GamePatches.tsx` `Facts` labels every non-draft PR “Ready for review” regardless of `eligibility.state`. Render **Blocked** as the primary status when blocked, retain the exact base-branch reason and actual configured requirements, and distinguish GitHub's open/draft state from merge eligibility.
2. `api.ts` `publicPull` derives `earliestBatch` from exposure time whenever policy is enabled, regardless of eligibility. Both detail/list UI advertise that value; the header also advertises a next merge batch. In advisory mode return no scheduled merge time and render “Not scheduled — advisory pilot.” Never infer future eligibility for a blocked PR from elapsed exposure alone.
3. On the actual governance baseline, add an explicit off-by-default server merge capability gate at the final GitHub mutation boundary and batch entry point. For today's pilot, keep all public vote paths incapable of GitHub approval or merging, even if legacy scheduling flags are permissive. A verified maintainer must make an explicit merge decision outside public vote aggregation. Do not create a second ambiguous enablement path or weaken existing gates.
4. Keep the direct URL readable with **“Developer preview / not a binding vote.”** Suggested explanation: “Community policy proposals express civic priorities. This developer PR preview is a separate advisory pilot. Public responses do not approve or merge code. A verified maintainer must explicitly decide whether to merge.” Keep developer PR entry points out of the main civic policy journey. Do not conflate preview availability with merge eligibility.
5. Preserve source repository IDs, repository/kind isolation, PR head/base revision binding, browser versus verified ballots, existing history, feedback receipts and stored data. Do not migrate or reset them for this gating task.
