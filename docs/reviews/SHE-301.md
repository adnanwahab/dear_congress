## Current implementation findings

- `src/client/App.tsx` routes `/published`, `/feed`, `/votes` and `/vote` to
  `WorkflowScreen`; `/needs` remains in `LegacyApp`. Updating only Dashboard or
  CitizenProposals would miss the requested launch routes.
- `src/client/WorkflowScreen.tsx` reads `/api/demo` and filters by topic and text.
  It displays jurisdiction labels but offers no jurisdiction browsing preference.
  Its selected item can remain outside the filtered list via `items.find` and
  `items[0]` fallbacks. A future picker must resolve selection within the applicable
  set, including an honest empty state, before enabling vote actions.
- `src/engine/demo.ts` labels scope as City, County, State or Federal. These are
  levels, not geographic IDs. Do not silently interpret every future City item
  as Houston or every County item as Harris County. The initial fictional fixture
  needs explicit, reviewed place mapping without changing its proposal IDs,
  source URLs or existing vote keys.
- Legacy Needs already groups priorities for Houston, Harris County, Texas and
  United States using `state.proposals[].jurisdiction`. It shows all four groups;
  a shared browsing preference must refine this view without changing journals,
  allocations, calculated demand, synthesis inputs or persisted votes.
- Citizen proposals have a separate advisory contract, including `unsure` and
  optional place names. Do not infer a verified constituency or fold those records
  into the sample demo's counts. Repository PR voting remains a separate system.

## Bounded implementation handoff after the gate

Use a shared, allowlisted manual selector with All jurisdictions (clear), United
States, Texas, Harris County and Houston. Prefer exact decision-body filtering
for this first version; explicitly say which scope is shown rather than implying
that selecting Houston establishes residence or includes every overlapping body.
Describe it as a browsing preference, never residency or voting eligibility.

Persist only the optional choice in a new browser-local key, catching storage
read/write failures and retaining a usable in-memory choice. Validate saved and
URL-supplied values if URL support is added. Unsupported values must visibly fall
back to All jurisdictions; do not silently guess a nearby locality. Clear removes
the stored preference. Never request device GPS or require signup.

Share the preference behavior across the three workflow routes and Needs. Use
native labeled selects, a keyboard-operable clear button, readable mobile layout
and a polite live scope/result-count note. Show proposal scope and possible office
as illustrative responsibility, not implemented authority or confirmed sponsorship.
Keep API payloads, source IDs and vote submission keys unchanged. Reset hidden
selection and stale office state when scope changes; preserve saved ballots.
