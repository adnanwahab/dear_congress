# SHE-938 — journal and civic vote retry receipts

Refs: https://linear.app/shel-bernstein/issue/SHE-938/cs-l100069-make-journal-and-vote-writes-idempotent-on-retry

## Evidence and scope

Inspected readme.md, AGENTS.md, docs/citizen-proposals.md,
docs/community-vote-batches.md and docs/launch-merge-policy.md before changes.
GitHub search for idempotent writes in adnanwahab/dear_congress returned PR #2
(existing proposal publication/comment dedupe) and PR #1 (isolated repository
voting). Their mechanisms remain unchanged. The active journal form uses
POST /api/entries; POST /api/journal and /api/publish_draft are additional write
paths. Contact-detail moderation can create a pending journal before the normal
handler. Civic /api/votes replacement is naturally duplicate-free, but a delayed
old request could restore an obsolete choice after a newer vote.

## Implementation

These four POST endpoints optionally accept an `Idempotency-Key` random UUID v4
header. Cookie-aware clients must establish and retain the server-issued browser
cookie before retrying. Keys are scoped by that existing anonymous identity and
exact endpoint; caller-supplied voter headers are still replaced by the security
boundary. Keys do not establish a verified voter or resident.

The server hashes the scope and canonical JSON payload. A successful first request
stores its status and JSON outcome in a private optional DB field, in the same
atomic JSON snapshot as the mutation. Same-key/same-payload requests replay that
outcome; changed payload returns 409; malformed keys return 400. Property order
is ignored, but whitespace within content and array order are significant.
Validation, origin checks, submission pause and rate limits still run before
receipt lookup, so those controls can reject even a replay. Requests without keys
remain supported with legacy retry semantics.

Public API object mutation handlers serialize within the existing single-process
writer. Keyed transactions defer handler saves and journal notifications/pipeline
start until the receipt is ready to commit. Failed commits restore the prior DB
and retain no successful receipt. Replay does not run extraction, create another
journal/fork, cast a vote, or undo a later vote. Simulation reset preserves retry
receipts. Existing public state serializers do not expose them.

The shared browser request helper retains one UUID for the same endpoint/body
following a failed or uncertain response, clearing it after success. This state
is page memory only; refresh loses the retry key. External clients can retain
keys across restart. Replaying /api/entries after server restart returns the same
fork ID, but the existing in-memory fork event stream is not restart durable.
The journal record itself is durable. No cross-process writer guarantee is added.

Receipts retain the original JSON response (including submitted journal content)
in the private DB without automatic expiry. They require the same protected
storage as journals; receipt lifecycle/erasure and growth limits need explicit
operator review before broader rollout. Whole-DB snapshots and serialized writes
can add memory/queue latency, especially during LLM extraction. No production
latency claim is made.

## Local measurement and validation

Measured entirely in local handler tests with empty databases and synthetic
requests, eight concurrent attempts with no key created eight records (seven
duplicates); eight attempts sharing a key created one record (zero duplicates).
A separate 20-way same-key test executes the mutation once and gives identical
202 outcomes. Tests cover receipt reload, browser/route isolation, changed-content
conflicts, later-vote preservation, save failure rollback and deferred effects.
These are bounded reliability measurements, not a public load test or HTTP latency
benchmark.

- Focused tests: 4 passed, 58 assertions.
- `bun run typecheck`: passed.
- `bun test`: final run 668 passed, 27 failed (695 tests, 127,320 assertions).
  HTTP tests cannot bind sockets in this sandbox;
  startup fails with EADDRINUSE on port 0. No assertion failure in the new focused
  tests was observed.
- `bun run test:routes`: blocked by the same socket binding failure.
- Added an isolated child-process HTTP regression for all three journal aliases,
  moderation holds, eight-way concurrency, conflicts, legacy baseline and vote
  replay across actual restarts. It is retained for a socket-capable runner and
  could not execute past startup here. It uses temporary data and empty provider
  credentials. Required HTTP checks must pass before human acceptance.

## Reversible staged rollout for a human release owner

1. Run all required checks in a socket-capable runner. Verify private receipt
   serialization and deletion/retention policy. Record local HTTP results and
   queue latency for one writer using temporary synthetic records only.
2. Review and release server support first to an isolated staging instance with
   existing data compatibility checked. Old clients omit keys and retain existing
   behavior. Rehearse lost responses, restart, changed-content conflicts and a
   newer vote followed by an old retry. Never submit public test records.
3. Enable the browser helper in a reviewed staging revision, then verify a mobile
   retry manually with an established cookie. Record duplicate creation rate and
   median/p95 duration for this bounded local scenario, including slow extraction.
4. A human may approve a tagged production release after all checks and privacy
   review. Observe existing queue/write-failure health without collecting keys,
   payloads or identity traces. Pause public submissions if rollback is required;
   revert the client helper before server rollback, preserving receipt fields and
   DB backups. Returning to an old server loses retry guarantees while it runs.
   No rollout or production mutation has been performed for this issue.
