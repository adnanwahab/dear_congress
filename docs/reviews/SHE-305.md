## Current behavior and gaps

- `src/shared/citizen-proposals.ts` stores immutable published free-text
  `proposedChange`, jurisdiction and optional source journal identity. Records
  contain private owner/idempotency hashes and per-browser advisory choices.
  There are no clause IDs, revision parents, author-publication permissions,
  amendment records or amendment ballots.
- `src/server/citizen-proposals.ts` publishes a new independent record; retries
  with the same key and different normalized content return 409. Public views
  explicitly omit private hashes. Writes serialize and roll back on save failure.
  Voting updates the selected proposal's choices; it has no revision target.
- `src/client/App.tsx` selects `WorkflowScreen` for `/draft`, `/votes` and `/feed`.
  `WorkflowScreen.tsx` provides illustrative sample drafting/comparison and
  separately exposes citizen proposal flows. The recovered route precedence
  matters: adding a control only to `CitizenProposals.tsx` will not cover every
  proposal displayed at `/votes`. Sample text must remain clearly illustrative.
- `src/engine/variants.ts` implements costing/delivery variants, not resident
  legal amendments. Neither those choices nor repository PR ballots can serve
  as amendment votes. Journal moderation is not amendment publication approval.

The existing free-text draft model is a starting point, not a structured legal
source. Establish stable clause identity and exact source snapshots before
exposing legal-text edits. Never describe sample clauses as enacted law.

## Proposed pilot contract (not current APIs)

Start with a small set of explicitly opted-in citizen proposals. Give their
initial text an additive immutable revision snapshot with stable clause IDs,
exact text, content hash, proposal ID, jurisdiction, source IDs and citation
metadata. Preserve original records, IDs, votes, comments and timestamps. Do not
infer clause boundaries as authoritative legal interpretation. Initially permit
one whole-clause replacement per suggestion; insertion/deletion can follow once
clause ordering and reference behavior are validated.

An amendment submission contains its own ID, proposal ID, exact base revision
ID/hash, clause ID and original text/hash, replacement text, rationale,
impact/cost note (including explicit unknowns), citations and publication consent.
Citations retain title, URL, locator, retrieval date and cited excerpt/version;
a citation is supporting evidence, not proof of correctness. Retain source
repository/item identity if an external item is referenced, without changing its
ballot namespace. Validate sizes, URL schemes and escaped rendering; do not fetch
arbitrary citation URLs on the server.

Separate private owner identity from an optional public display name. Default to
an unverified participant label. Public display-name attribution requires explicit
permission, separate from permission to publish amendment text/rationale/citations.
Record the consent version, time and exact submitted content hash. Never expose
cookie IDs, hashes, private feedback or local drafts. Pending submissions are
visible only to their owner and authorized moderators; public comparison begins
only after publication approval. Explain that previously public copies may persist.

Submission creates an immutable candidate and a private review event. A moderator
can reject, request changes or approve a specific content hash with a reason and
authenticated actor. Approval must atomically create the public revision/option
and its audit event, or create neither. Changed text or consent requires a new
candidate and renewed review; moderator approval cannot silently edit an author's
words. Existing journal-admin infrastructure may be reused only after defining
amendment authorization, ownership and private-feedback boundaries. Preserve
signed-cookie identity, origin checks, limits and explicit public confirmation.

Proposed state transitions are local draft → pending review → published,
rejected or changes requested. Conflict is a publication blocker with private
author feedback. Resubmission creates a new candidate linked to the prior one.
Immutable snapshots are separate from append-only decision/status events.

Each published alternative has its own option ID bound to its exact revision.
Existing proposal ballots remain on the original proposal and are never copied
or reinterpreted. New amendment responses start at zero, use separate keys and
show separate denominators. A newer revision does not inherit older choices.
Retain historical choices if an option is withdrawn; label its status and reject
new votes on withdrawn/unpublished options. All results remain browser-based,
advisory and self-selected, never governmental or verified merge authority.

## Conflicts and reconstruction

Check the submitted base and clause hash again inside serialized publication.
Two suggestions against the same base may be independently compared alternatives;
neither automatically overwrites the other. Combining them requires a new derived
candidate naming all contributing revisions and authors. Overlapping edits or a
changed/deleted clause block combination. Return 409 with a safe conflict summary
to the owner, retain the submitted candidate and show base/current/proposed text.
The author explicitly chooses a replacement against the new base, then submits
for fresh moderation. Even nonoverlapping combinations require author review;
there is no silent rebase or automatic legal-text merge.

Persist full revision snapshots and ordered audit events recording submission,
parent links, consent, moderation, publication, conflict and supersession. Store
actor references privately and a consented public attribution separately. A
replay must recover each published text, its inputs, approval and option identity
without consulting mutable URLs or rerunning a diff algorithm. Hashes detect
mismatch but do not themselves make an editable JSON file tamper-proof. Define
backup/recovery and integrity checks before claiming an auditable production
history. Public removal should suppress sensitive display content while retaining
access-controlled audit evidence under a documented retention policy; immutable
history must not promise permanent public exposure of personal information.

## Walkthrough and acceptance fixtures

Use isolated temporary storage and two browser contexts; never submit test
amendments to production. Pilot fixtures are illustrative, not legal advice.

1. Publish P0 with clause C1: “The pilot shall run for 12 months.” Browser A votes
   support on P0. From `/votes`, open Suggest amendment and compare against P0.
2. Browser B replaces “12” with “18”, supplies rationale “Observe two summer
   seasons”, cost note “Additional cost unknown”, and a clearly labelled fixture
   citation. Choose public attribution and separately confirm public content.
3. Submit; B sees pending status and retained text after reload, while A sees
   neither candidate text nor a new voting option. An unauthorized moderation
   request fails. An authorized moderator approves the exact candidate hash.
4. A sees side-by-side P0/P1 with revision IDs, dates, source, permitted authorship,
   rationale, citation and explicit removed/added text. P0 retains its one vote;
   P1 starts at zero. Vote on P1, then withdraw it: P0 is unchanged.
5. Another author proposes “24 months” from P0. Compare both alternatives. Attempt
   to combine with P1: show the overlapping-clause conflict, preserve both inputs,
   send owner-visible feedback and require a new reviewed submission.
6. Restart, reconstruct P0/P1 and their audit lineage, and verify independent vote
   totals and consent. Reset the simulation and verify all these records survive.

| Fixture / edge case | Required evidence before acceptance |
| --- | --- |
| Same idempotency key, same body / changed body | One candidate / 409; no duplicate publication or audit event |
| Blank, unchanged, oversized, Unicode or repeated-clause text | Useful validation; stable clause identity; exact text preserved |
| HTML/script in text/name; unsafe citation URL | Escaped display; unsafe link rejected; no script execution |
| Missing, foreign-proposal or stale base/clause | Reject or explicit conflict; no parent overwrite |
| Concurrent approvals and save failure | One option per candidate; atomic durable state or complete rollback |
| Lost response, reload and restart | Retry recovers same submission; pending text stays private |
| Rejected candidate, absent consent or altered candidate | No public option; fresh consent/review required for changed text |
| Cookie loss, forged owner ID, foreign origin, rate overflow | No ownership adoption or moderation bypass; existing protections hold |
| Sample / citizen / engine / repository PR or issue IDs collide | No shared ballots, inferred authorship or transferred source identity |
| Hidden source or revoked attribution | No private source leak; documented removal and audit treatment |

Accessibility acceptance requires keyboard-only editing, comparison, submission
and conflict recovery; visible focus; associated labels and errors; announced
pending/error/success states; and focus management on validation/conflict. Show
“Removed” and “Added” in text as well as color/strike/underline. Side-by-side
columns must have explicit revision headings and a logical reading order, with
stacked narrow-screen and linear screen-reader views. Test zoom, contrast, long
clauses and citations, and native screen-reader output. No browser/accessibility
acceptance is claimed by this document.
