Implementation candidate only. Keep the issue open pending human acceptance,

## Audit and implementation

Reviewed repository instructions, README, citizen-proposal documentation,
SHE-325 tally review and launch merge policy. The API already keeps fixture
counts in `items` and cookie-based choices in `browserCounts`. WorkflowScreen
showed separate text counts but its voting buttons still presented fixture
numbers; Dashboard also used those numbers on buttons and in its footer.

Both surfaces now pass only `browserCounts[item.id]` to non-live choice controls.
Their named region and heading say “Unverified browser choices”; buttons retain
explicit actions and selected state, with descriptions of cookie/eligibility
limits. Missing counts say unavailable and never fall back to fixture numbers.
The separate fictional figure contains a heading, descriptive accessible text,
static labeled counts and decorative bars, with a dashed border, spacing and no
interactive vote controls. The total is labeled fictional at its point of use;
no real-person KPI is introduced. Live round counts retain their existing path.
Downloaded sample drafts also label their totals fictional and exclude people/browser-choice claims.
Existing submissions, acknowledgments, receipts, source selection and persisted
records are unchanged. No API, database or aggregation behavior was changed.

Connected GitHub search for SHE-794 returned no matching PR. A broader open-PR
search found concurrent SHE-795/#386 (source chips), SHE-796/#385 (production vote
verification), SHE-797/#384 (Skip), and SHE-798/#383 (post-vote next steps). Read
#384's diff: it changes AdvisoryVoteBars, its styles/tests and the public guide.
Preserve its equal-choice Skip behavior when integrating; this work does not
replace that PR. CLI GitHub access failed. This audit is not evidence of an
exhaustive conflict check or production acceptance.
