## Reversible staging drill for the recovery operator

1. Identify the exact source SHA/image, staging hostname and disposable volume;
   verify they cannot mount production storage. Restrict access and outbound
   connections. Use fresh staging secrets; omit GitHub/provider/publishing tokens,
   disable workers and automatic actions, retain fail-closed governance. Do not
   start a recovered outbox with live credentials. Record rollback owner and time.
2. Create only clearly labelled synthetic fixtures: owned journal, unrelated
   journal, civic and citizen-proposal responses from two browser jars, proposal
   linked to a journal, frozen plan, and repository PR/issue records with distinct
   source/head/base revisions and retained receipts. Never infer verified voters
   or present fixture totals as public participation. Hash a private manifest of
   IDs, source links, revisions, record counts and expected projections.
3. At low sequential staging traffic, measure before-backup read/write latency,
   errors and counts. Quiesce all writers and drain JSON saves/background work.
   Capture one consistent recovery set across JSON and both SQLite stores using
   SQLite-supported backup facilities; never copy a live main SQLite file alone
   while ignoring its WAL. Record snapshot time, source SHA and checksums. Restore
   into a new directory/volume; never overwrite the source or current target.
4. Encrypt the complete archive using an operator-reviewed authenticated scheme
   (candidate AES-256-GCM with fresh nonce and a random data key wrapped by a
   separately held recovery key). Authenticate the manifest too. Verify wrong-key
   and corruption failures before application startup, and test recovery by a
   second authorized operator. Do not log keys or plaintext. Record actual cipher,
   key custodian, access controls, independent storage and approved finite expiry;
   a proposed cipher is not evidence the existing backup uses it.
5. After the snapshot, delete one owned fixture journal and withdraw both kinds
   of advisory response. Preserve the current removal evidence independently of
   the older snapshot. Simulate loss only in the disposable staging target.
   Decrypt/verify to quarantine, check SQLite integrity, start the pinned image
   with workers/egress disabled and compare the private manifest before exposure.
6. Reconcile post-snapshot removals before reopening access. The inspected journal
   deletion removes active text/owner mapping and clears linked snapshot location;
   it preserves independently published proposal text/source IDs. An old backup
   can resurrect removed entries and votes. No general durable deletion-tombstone
   replay protocol was demonstrated. If current removal evidence cannot be
   reconciled safely, keep the restore quarantined and fail the drill.
7. Verify owner deletion succeeds, stranger/cross-origin deletion fails, deleted
   content is absent from feeds/APIs/needs/SSE after restart, and unrelated records
   survive. Verify civic `withdrawVotes`/null goal votes and citizen response
   `choice:null` persist after restart without changing another browser's choice.
   Check proposal source IDs, repository/item boundaries, exact PR head/base
   bindings, existing revisions/freezes/receipts and absence of external writes.
   Metrics retaining earlier participation must not be mistaken for active votes.
8. Measure after-restore latency/errors using the same small sequential sequence;
   compute RPO from snapshot age at simulated loss and RTO from loss declaration
   to validated availability, including reconciliation and operator time. Record
   archive bytes, encrypt/decrypt/restore durations, integrity results and failures.
   Switch only the isolated staging target after validation; rollback by stopping
   it and selecting its preserved prior volume/image. Destroy fixture plaintext,
   archives and drill keys after recording the agreed expiry/cleanup outcome.

No public load test is needed or authorized. Production rollout requires a separate
human-reviewed tagged release and an explicit recovery/removal policy. Do not
promise indefinite retention, guaranteed erasure or a numeric RPO/RTO before the
operator verifies the actual configuration and rehearsal.
