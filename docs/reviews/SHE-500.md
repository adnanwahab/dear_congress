## Proposed typed implementation contract

These are proposed contracts, not implemented endpoints or migrations.

1. Add immutable `PlanRevision` records with a versioned schema, opaque revision
   ID, content digest, exact source repository/build revision when known, explicit
   source kind and item ID, parent revision IDs, creation time and private owner
   reference. Freeze ordered plan items, exact text, assumption schema/version,
   jurisdiction, citations and their provenance, units/horizon, unknown values
   and real/synthetic labels. Unknown source revision stays unknown. Do not infer
   eligibility or clause boundaries from prose. A sample source and a citizen
   source with the same ID must never share ancestry or review records.
2. Fork an existing immutable revision; keep its ID as the parent. Edits create
   another immutable revision. Keep editable workspace state separate from saved
   revisions. Never reconstruct a historic parent from today's catalog. Validate
   parent scope, existence, duplicates, cycles, schema and graph bounds. Coordinate
   legacy local lineage with #150; do not invent ancestry for older versions or
   silently upload private drafts. Use a new server store, not localStorage as
   durable authority and not the evicting simulation snapshot array.
3. Define `MergeRequest` with source revision ID/digest, target branch and exact
   expected target revision, common ancestor, candidate revision/digest, rationale,
   permissions and request state. Use server-issued ownership, same-origin/CSRF
   protections, bounded validation, serialized writes and retry idempotency.
   Identical retries return the original request; changed content on the same key
   conflicts. Submission is a private review request, not publication consent.
4. Add append-only `ReviewDecision` records: request ID, exact candidate and target
   digests, authenticated reviewer reference, role/policy version, decision,
   reason and server timestamp. Establish a named civic reviewer authorization
   policy before enabling decisions. Do not reuse advisory browser responses,
   proposer cookies or GitHub repository membership as implicit civic authority.
   Author self-approval must not satisfy independent review. Decisions on an old
   candidate or target remain historical and cannot approve a new candidate.
5. A deliberate authorized combine operation rechecks permissions, required
   decisions, conflicts and expected target inside the single-writer transaction.
   It atomically appends a new revision naming both parents, advances the target
   and records the decision linkage, or changes nothing. Failed persistence rolls
   back all three. Concurrent requests against one target cannot both advance it
   from the same expected head. Preserve source drafts and historical decisions.
6. Combining only creates a reviewed civic draft. Publication remains a separate
   explicit, permissioned action with content-bound consent and moderation.
   No auto-publication, law-status promotion, official sponsorship, enacted-law
   label, new ballot or inherited vote follows a merge. Existing civic votes,
   repository ballots, source records, PR head/base bindings and receipts stay
   untouched. No compiler from edited text to simulation is implied.

Reviewer role assignment and the approval rule need a product/security decision;
this review does not configure quorum one or import the developer quorum into
civic plan review. Until a policy is established, offer preparation and comparison
with review unavailable, rather than simulated approval presented as real.

## Conflict and comparison rules

Use three-way comparison of common ancestor, current target and proposed branch.
An unchanged side is distinct from a concurrent change. If both sides change the
same field differently, require explicit resolution; identical changes agree.
Deletion versus modification, missing ancestors, incompatible schemas or units,
and cross-source ancestry block combination. Disjoint field edits may prefill a
candidate, but still require human review of the complete candidate. Never silently
rebase, overwrite the target or treat a fresh start as a resolved old request.

Expose text, cost and eligibility as separately named conflict groups. Present
ancestor/current/proposed values and a side-by-side current/proposed diff using
Added/Removed text as well as styling. Cost compares numeric amount, currency,
scale, period and estimate provenance; unknown is not zero. Recompute the full
candidate ledger, detect budget overflow and retained rights exclusions, and
distinguish arithmetic feasibility from independently verified cost. Eligibility
must be explicit participant-entered structured criteria with unknown values;
changed geography, thresholds, exclusions and affected groups need review even
if text edits do not overlap. Cross-field contradictions can block a candidate
despite no same-field conflict. Do not claim automatic legal/rights correctness.

Resolution creates a new candidate revision with the resolving actor/reason and
retains both alternatives and citations. It invalidates approval applicability
and requires fresh review. Stale targets return a conflict response with safe
current revision identity; unsaved user input and previous request remain intact.

## Six-stage UI and acceptance matrix

Keep Published/Feed source provenance and selected source intact. Votes may link
to a branch but cannot cast a choice by navigation or copy original responses.
Draft offers Fork snapshot → Edit assumptions → Compare → Request review, plus
read-only request/decision history. Sponsors can prepare outreach from an exact
reviewed revision without sending it; Outcomes distinguishes draft history and
simulated activity from actual government action. A synthesized package needs an
explicit frozen-package entry from Synthesize; do not relabel a sample proposal
as the user's current package. Preserve topic, jurisdiction and proposal selection
on navigation. Review links must carry opaque IDs, never private draft text,
journals, cookie identifiers or locations.

| Area | Required focused evidence before acceptance |
| --- | --- |
| Fork/edit/replay | Parent immutability across reload/restart; exact source/text/assumptions/citations; legacy retention; no parent or vote mutation |
| Conflicts | Text overlap, differing cost units, unknown cost, eligibility changes, delete/edit, disjoint changes, identical changes, budget overflow, rights exclusion and missing ancestor |
| Review authority | Unauthorized and self-review rejection; exact candidate/target binding; new edit/target invalidates applicability; historical decisions retained |
| Persistence | Same-key retry, different-body conflict, simultaneous target advance, rollback on disk error, restart replay and capacity failure without eviction |
| Privacy/consent | No implicit upload/publication; safe public projection; no owner hashes or private journal/location leakage; citation text escaped, URLs never fetched blindly |
| Loading/failure | Named loading state; stale response cancellation on source change; initial and refresh failures; not-found/unauthorized/stale-target states; uncertain-save reconciliation before explicit retry; retained editing input |
| Mobile/keyboard | 390px and actual 200% zoom; comparisons stack with headings; all actions native labelled controls; no drag/hover dependency; visible focus, error focus, live status and logical reading order |
| Reduced motion | Shared motion tokens/helper; full static diff and conflict text with reduced motion and motion=off; no meaning conveyed only by animated branches |

Use isolated local fixture data, model tests for graph/review invariants, handler
tests for auth/concurrency/rollback, and DOM tests for editor/request composition.
Real-browser keyboard, screen-reader, mobile/zoom and reduced-motion walkthroughs
must exercise the expanded branch/review panel; default route screenshots alone
cannot establish acceptance. Include a two-browser authorized reviewer journey
and a failed/stale request, without contacting production.
